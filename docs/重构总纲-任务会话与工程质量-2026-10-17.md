# J.Co 重构总纲：从功能堆叠到任务型 AI 工作台

> 结论先行：当前的问题不是“还有几个细节没修”，而是**产品模型没有定死，导致聊天、任务、自动任务、员工、浏览器、页面各干各的**。继续发现一个补一个，只会不断制造新的细节问题。
>
> 下一步不是马上再改首页或再调 CSS，而是先完成**需求基线 → 领域模型 → 交互冻结 → 一条纵向链路 → 再复制到各工作流**。

---

## 一、现状诊断：为什么会“一团糟”

| 现象 | 直接根因 | 代码证据 |
|---|---|---|
| 总管一开口就说“成人学历提升招生” | 系统提示词把行业写死 | `app/kernel/bridge.mjs:101` |
| 首页发一句话变成任务，甚至打开浏览器 | 首页输入直接调用 `tasks.dispatch`，没有“聊天 / 派活”区分 | `设计原型/J.Co主界面-首页.html:304`、`app/main.js:894` |
| 聊天和任务像两套东西硬撮合 | 所有会话都走同一套 `buildChatSystem()`，任务只额外拼一段纪律 | `app/kernel/bridge.mjs:611`、`app/main.js:840` |
| 聊天里可能自己开浏览器 | 浏览器工具 patch 对聊天和任务都常驻挂载 | `app/kernel/bridge.mjs:416-417` |
| 消息每条都是巨大的圆角卡片 | AI 消息 body 最宽 84%，bubble 又加卡片背景、阴影和 16px 字号 | `设计原型/J.Co总管.html:79-89` |
| 长回答重新打开后被截断 | 入库时每条消息硬截 2000 字 | `设计原型/J.Co总管.html:492` |
| Markdown 排版差 | `mdToHtml` 只处理加粗和换行，没有段落、列表、代码块 | `设计原型/J.Co总管.html:424` |
| 自动任务和派活记录对不上 | 自动任务写 `auto-runs.json`，派活写 `task-sessions/*.json` | `app/main.js:663`、`app/main.js:840` |
| 前端总在补丁式修改 | 页面仍是多份 HTML + 各页自己的脚本和局部样式 | `设计原型/*.html` 与 `assets/jco-shell.js` |
| 测试绿了但用户仍觉得不能用 | 大量测试在验证“元素存在 / 源码包含某段字符串”，没有验证真实体验 | `app/tests/e2e/*.spec.mjs` |

### 1.1 最深的一层问题

现在的实现把下面这些概念混在了一起：

```text
聊天会话
任务
自动任务
AI 员工角色
浏览器会话
页面导航
```

它们在代码里都表现为“发一段 prompt，调用内核，然后显示结果”。这就是为什么首页聊天会变成任务、任务会像聊天、聊天会打开浏览器、自动任务和派活各写一套记录。

**必须先定清楚“谁是什么”，再谈怎么实现。**

## 二、目标产品模型

### 2.1 八个核心对象

| 对象 | 一句话定义 | 关键字段 | 不应该做什么 |
|---|---|---|---|
| **Conversation（会话）** | 用户与助手的对话线程 | id、title、messages、model、createdAt、updatedAt | 不默认产生外部副作用；不直接启动浏览器 |
| **Task（任务）** | 一张可执行的工作单 | id、title、goal、type、ownerRole、inputs、constraints、deliverables、approvalPolicy、status、parentId、sourceConversationId | 不是聊天消息流；不靠标题猜状态 |
| **TaskRun（执行）** | 任务的一次实际执行 | id、taskId、status、startedAt、endedAt、logs、toolCalls、artifacts、error、attempt | 不和任务混成同一个对象 |
| **Automation（自动任务）** | 按计划创建任务的模板 | schedule、taskTemplate、enabled、lastRun | 不另起一套执行台账 |
| **AgentRole（员工角色）** | 一类岗位的职责、技能、工具权限和提示词 | id、name、skills、allowedTools、promptProfile | 不是聊天人格；不能拿到超出职责的工具 |
| **BrowserSession（浏览器会话）** | 某个平台的可复用浏览器资源 | platform、profile、endpoint、token、status | 不是任务；不能由纯聊天随意启动 |
| **Artifact（产物）** | 任务或会话产生的文件/草稿/报告 | id、kind、path、taskId、conversationId、createdAt | 不能只存在页面内存里 |
| **Approval（确认点）** | 需要用户拍板的人机检查点 | id、taskId、type、reason、options、status | 不能被“全自动”模式绕过 |

### 2.2 关系图

```text
用户
  │
  ├─ 发起 → Conversation（聊天）
  │             │
  │             └─ 提出任务卡 → 用户确认 → Task
  │
  ├─ 直接创建 → Task
  │
  └─ 配置 → Automation ──到点/马上跑──→ Task
                                          │
                                          ├─ 分配给 AgentRole
                                          ├─ 创建 TaskRun
                                          ├─ 需要时申请 BrowserSession
                                          ├─ 产生 Artifact
                                          └─ 到 Approval 停下等用户
```

### 2.3 边界规则

1. **聊天不是执行器。**
   - 聊天可以理解需求、拆解任务、写任务卡、解释结果；
   - 聊天默认不调用发布、浏览器、文件写入等有副作用的工具；
   - 聊天要执行，必须先形成任务卡并经用户确认。

2. **任务不是聊天。**
   - 任务有自己的详情页、状态机、过程日志、产物和审批点；
   - 任务可以在聊天里被“提及”，但不能把聊天消息流当成任务详情。

3. **自动任务不是第二套任务系统。**
   - `Automation` 只负责“什么时候创建任务”；
   - 到点执行和“马上跑”都创建同一种 `Task` / `TaskRun`；
   - 总管任务区必须能看见自动任务产生的任务。

4. **员工不是聊天人格。**
   - 聊天人格负责对话；
   - 员工角色负责执行任务；
   - 两者的提示词、上下文和工具白名单必须分开。

5. **浏览器是资源，不是默认动作。**
   - 只有任务明确需要发布、运营、登录、平台数据时，才申请对应平台的浏览器会话；
   - 任务结束或失败后，按策略回收；
   - 纯聊天、写稿、选题、图片生成不应启动浏览器。

### 2.4 任务状态机

```text
draft
  → pending_confirm（等待用户确认任务卡）
  → queued（已确认，排队）
  → running（执行中）
      ├─ waiting_user（等待审批 / 登录 / 选择）
      ├─ done（完成，产物已登记）
      ├─ failed（失败，保留错误和重试入口）
      └─ cancelled（用户取消）
```

规则：

- 进入 `running` 前必须有完整任务卡；
- 进入 `waiting_user` 时必须说明“在等什么、用户要点什么”；
- `done` 不等于“模型说完成”，必须有产物或可核对结果；
- `failed` 必须保留失败步骤、错误摘要和下一步建议；
- 任何重试都是新的 `TaskRun`，不能覆盖上一次记录。

### 2.5 首页 → 新会话 → 任务卡的完整链路

```text
首页输入一句话
  → 创建/进入一个独立 Conversation
  → 聊天助手回答、澄清或提出任务卡
  → 用户点“确认派活”
  → 创建 Task（带目标/输入/产出/约束/审批点）
  → 进入任务详情页
  → 选择/自动分配 AgentRole
  → 执行 TaskRun
  → 需要时启动 BrowserSession
  → 到审批点停下
  → 用户确认
  → 完成并登记 Artifact
```

这条链路是 Phase 1 的验收主线。它同时解决首页、会话、任务、浏览器和可操作性五个问题。

## 三、目标体验

### 3.1 首页

- 输入框默认是**聊天入口**，发送后进入一个独立会话；
- 输入框旁边或下方提供明确的“派活”入口；
- “派活”不是静默执行，而是先展示任务卡，让用户确认目标、输入、产出和审批点；
- 首页不再自动打开浏览器；
- 首页的快捷卡片只负责填充输入或打开对应页面，不直接产生副作用。

### 3.2 聊天页

- 一个助手，多个独立会话；
- 消息从上往下，第一句话从顶部开始；
- 输入框固定在底部，不随消息数量漂移；
- 历史记录支持重命名、删除、分享、复制；
- 会话切换不卡死、不丢消息、不把任务视图混进来；
- 消息内容完整保存，不再 2000 字截断；
- Markdown 至少支持段落、标题、列表、引用、代码块、链接和加粗；
- AI 消息使用“头像 + 平坦正文”的阅读布局，不再每条都是巨大圆角卡片；
- 用户消息右对齐气泡，AI 消息左对齐正文；
- 字号、行高、最大阅读宽度统一，长文可读；
- 复制、引用、创建任务、删除等操作在消息级别可用。

### 3.3 任务详情页

任务详情页必须独立于聊天页，至少包含：

```text
标题 / 状态 / 负责人角色 / 创建时间
目标
输入（会话、文件、链接、账号平台）
约束与红线
产出要求
审批策略
执行时间线（每一步在做什么）
产物列表
失败/重试/取消/确认按钮
```

任务详情页是“过程与结果可视化”的主舞台，不是聊天记录的另一种皮肤。

### 3.4 侧栏

- “对话”和“任务”两个分区视觉上明确不同；
- 对话项显示标题、最后更新时间和未读状态；
- 任务项显示状态徽标（排队/执行中/等你确认/完成/失败）；
- 点击对话进入会话，点击任务进入任务详情；
- 自动任务产生的任务和页面派活产生的任务出现在同一个任务区。

### 3.5 全站组件

- 一套按钮、输入框、弹窗、消息、任务卡、状态徽标、空态和提示；
- 共享样式只从 `设计原型/assets/jco-ui.css` 取；
- 页面只负责自己的业务视图，不再各自复制侧栏、输入台和助手球；
- 深浅色主题跨壳和 iframe 一致；
- 页面切换不闪烁、不跳动、不重绘侧栏。

## 四、目标技术架构

### 4.1 分层

```text
Renderer（应用壳 + 视图组件）
  │ 只做展示和用户交互
  ▼
Application（用例层）
  │ 会话用例 / 任务用例 / 审批用例 / 自动任务用例
  ▼
Domain（领域层）
  │ Conversation / Task / TaskRun / Automation / AgentRole / Approval
  ▼
Adapters（适配层）
  ├─ DSH 内核适配器
  ├─ 浏览器会话适配器
  ├─ ffmpeg / 文件适配器
  ├─ 数据存储适配器
  └─ 通知适配器
```

原则：

- 页面不直接拼 prompt；
- 页面不直接读写多个 localStorage key 拼业务状态；
- 页面不直接启动浏览器；
- 所有副作用通过用例层和明确的契约发生。

### 4.2 提示词分层

```text
Base Prompt（通用）
  ├─ 语言、诚实、安全、工具使用原则
  └─ 不包含任何行业、平台、岗位

Chat Prompt（聊天）
  ├─ 理解需求、澄清、拆解任务、提出任务卡
  └─ 不包含发布浏览器操作步骤

Role Prompt（员工）
  ├─ 选题 / 文案 / 视频 / 后期 / 发布 / 运营
  └─ 只能拿到该角色的工具白名单

Context（上下文）
  ├─ BrandProfile：行业、受众、语气、平台、目标、禁用表达
  ├─ TaskCard：目标、输入、产出、约束、审批点
  └─ Skills / PlatformRules / 外部资料（明确标记为资料而非指令）
```

**关键实现要求：**

- 不再把整段系统提示词拼进用户消息；
- DSH SDK 的 `RunOptions` 没有 `system` 字段，必须通过 DSH 的 system-prompt / persona / agent-preset / 独立 profile 机制注入，或为不同角色使用独立 harness；
- 聊天和员工使用不同的 prompt profile；
- 每个角色只挂自己的工具 patch；
- 纯聊天不挂浏览器工具；
- 发布员工只挂浏览器工具，不挂任意 shell / 文件工具。

### 4.3 数据层

目标：一个事实源，版本化 schema，可迁移、可回滚。

推荐顺序：

1. 优先使用 SQLite（事务、查询、分页、迁移都成熟）；
2. 如果 Electron 原生模块打包风险暂时不可接受，先用单一 JSON 存储 + schemaVersion + 原子写入作为过渡；
3. 无论选哪种，都不允许继续把聊天、任务、自动任务、产物分散在多个 localStorage key 和多套 JSON 文件里各自演化。

核心表/集合：

```text
conversations
messages
tasks
task_runs
task_events
automations
agent_roles
artifacts
approvals
settings
```

### 4.4 任务台账统一

必须删除“自动任务一套、派活一套”的分叉：

```text
Automation → Task → TaskRun → TaskEvent → Artifact
页面派活   → Task → TaskRun → TaskEvent → Artifact
手动创建   → Task → TaskRun → TaskEvent → Artifact
```

同一个任务在总管、自动任务页、团队页、通知里看到的是同一份状态。

## 五、工程流程：这次按什么顺序做

### Phase 0：冻结与建模（先不写功能代码）

目标：把“做什么、谁负责、怎么验收”定死。

交付物：

1. 本需求基线与产品负责人确认；
2. 领域模型（Conversation / Task / TaskRun / Automation / AgentRole / Approval）；
3. 首页、聊天、任务详情、侧栏的线框图和交互说明；
4. 提示词分层与工具权限矩阵；
5. 数据 schema 与迁移方案；
6. ADR：聊天与任务分离、提示词注入方式、任务台账统一、浏览器工具权限；
7. 验收用例骨架（先写会失败的测试）。

退出标准：

- 产品负责人确认“首页默认聊天、派活显式确认”；
- 所有对象边界没有歧义；
- 每个 Phase 1 用例都能写出 Given/When/Then；
- 没有这份冻结包，不允许写 Phase 1 功能代码。

### Phase 1：一条完整纵向链路

目标：把最小但完整的核心链路做对，而不是先铺满所有页面。

范围：

```text
首页 → 新建会话 → 聊天 → AI 提出任务卡 → 用户确认
→ 任务详情 → 任务执行（先用模拟内核）
→ 需要浏览器时启动 → 审批点停下 → 完成产物
```

同时完成：

- 消息组件重做（排版、Markdown、完整存储、历史操作）；
- 聊天 / 任务提示词分离；
- 聊天不挂浏览器工具；
- 任务统一台账；
- 任务详情页；
- 侧栏对话/任务分区；
- 深浅色和窄窗口适配。

退出标准：

- 一条 E2E 真实走通；
- 一条视觉回归覆盖聊天和任务详情；
- 一条集成测试覆盖任务状态机；
- 安装版冒烟通过；
- 产品负责人按“陌生人的眼睛”走一遍，不需要开发者提示。

### Phase 2：通用化与行业解耦

目标：把写死的行业内容全部移到可配置档案。

范围：

- 新增 BrandProfile：行业、受众、语气、平台、目标、禁用表达；
- 清理系统提示词、页面示例、默认任务、发布模板中的“成人学历”；
- 所有页面的生成提示改为从 BrandProfile + 页面任务上下文组装；
- 迁移老数据，兼容已有用户设置；
- 新增“账号定位”设置/引导页；
- 增加一条测试：切换到任意行业后，系统提示词和默认示例不出现旧行业。

退出标准：

- 全项目搜索不到写死的行业身份；
- 换行业后同一套工作流照常运行；
- 页面示例使用中性文案。

### Phase 3：逐个工作流做成“任务模板”

按标准自媒体工作流逐个落地，每个环节都必须有：

```text
任务卡模板
输入 / 产出定义
员工角色与技能
工具白名单
审批点
失败与重试
产物登记
过程时间线
```

顺序建议：

1. 选题 / 对标
2. 文案 / 脚本
3. 图片 / 视频创作
4. 后期
5. 发布（抖音先跑通，再复制平台适配）
6. 运营数据
7. 评论 / 私信 / 引流

每个工作流都必须有真实内核 + 真实工具 + 真实产物的验收，不仅结构断言。

### Phase 4：可靠性与安全

- 统一任务台账和事件日志；
- 工具超时、重试、幂等、并发限制；
- 浏览器会话生命周期；
- 发布 / 删除 / 支付审批门；
- 上传路径白名单；
- 外部内容数据/指令分隔；
- 错误码与用户可读错误；
- 安装包签名、自动更新策略；
- 日志脱敏与本地数据边界。

### Phase 5：发布验收

- 全量单元 / 契约 / 集成 / E2E / 视觉回归；
- 安装版冒烟；
- 真实内核冒烟；
- 真实浏览器 / ffmpeg 冒烟；
- 跨分辨率、深浅色、长会话、断网、失败恢复；
- 存档、回滚说明、CHANGELOG、tag；
- 产品负责人最终验收。

### 时间预期

以当前基础，Phase 0 约 2–3 个工作日，Phase 1 约 5–8 个工作日；完整走完 Phase 2–5 通常需要 4–6 周，具体取决于真实平台自动化和素材/ffmpeg 链路。**Phase 1 结束时应该能看到一个真正可用的核心闭环，而不是又一批页面。**

## 六、测试与验收体系

### 6.1 测试分层

| 层 | 测什么 | 工具/方式 | 不替代什么 |
|---|---|---|---|
| 单元测试 | 任务状态机、提示词组装、数据迁移、权限判断 | Vitest | 不能证明真实用户动线 |
| 契约测试 | IPC、DSH 工具、浏览器工具、ffmpeg 工具的参数与错误 | Node test / 模拟适配器 | 不能证明页面交互 |
| 集成测试 | 会话 → 任务 → 执行 → 审批 → 产物 | 真实数据层 + 模拟内核 | 不能证明安装版 |
| E2E | 首页、新会话、历史操作、任务详情、审批、侧栏 | Playwright Electron | 不能覆盖所有边界 |
| 视觉回归 | 消息排版、任务详情、空态、深浅色、窄窗口 | Playwright 截图对比 | 不能证明业务正确 |
| 安装版冒烟 | 启动、入口、侧栏、内核、真实模型 | 安装包 + 隐藏窗口 | 不能替代真实平台操作 |
| 人工验收 | 普通用户能否不看说明完成 | 产品负责人实测 | 不能被机器测试替代 |

### 6.2 必测用户旅程

1. 首页输入一句话 → 进入新会话 → 消息从上往下显示；
2. 新建会话 → 发消息 → 切换另一个会话 → 再切回来，内容完整；
3. 历史会话重命名 / 分享 / 删除；
4. 聊天中 AI 提出任务卡 → 用户确认 → 任务详情 → 执行 → 完成；
5. 纯聊天不启动浏览器；
6. 发布任务启动对应平台浏览器 → 快照 → 操作 → 停在发布前；
7. 自动任务到点 → 生成同一种任务 → 任务区可见 → 完成通知；
8. 深浅色切换 → 壳和内容区一致；
9. 侧栏展开 / 收起 / 再展开；
10. 1280×800 和 1440×900 下对话、任务详情不溢出。

### 6.3 Definition of Done

一个功能只有同时满足以下条件才算完成：

- 需求基线中的对应条目已写明；
- 交互稿 / 任务卡 / 数据契约已冻结；
- 有会失败的验收用例，并且现在通过；
- 单元 / 契约 / 集成 / E2E / 视觉回归按风险覆盖；
- 安装版和真实内核冒烟通过；
- 文档、CHANGELOG、截图/录屏证据齐全；
- 产品负责人按普通用户视角验收通过。

## 九、最终结论

这次不再用“再修一个页面、再补一个按钮”的方式交付。

正确的顺序是：

```text
需求基线
  → 领域模型和交互冻结
  → 一条完整纵向链路
  → 通用化行业配置
  → 逐个工作流做成任务模板
  → 可靠性与安全
  → 全量验收和交付
```

只要 Phase 1 的“首页 → 新会话 → 聊天 → 任务卡 → 任务详情 → 执行 → 审批 → 产物”真正跑通，后面的选题、文案、视频、后期、发布、运营才有同一条地基可以复用；否则每加一个功能，都会继续长出新的“细节问题”。
