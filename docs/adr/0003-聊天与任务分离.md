# ADR-0003：聊天与任务分离

- 日期：2026-10-17
- 状态：已采纳（M11 Phase 0）
- 关联：`docs/plans/M11-任务会话重构/领域模型与交互冻结.md`

## 背景

当前首页发送直接调用 `tasks.dispatch`，聊天变成了任务；总管、派活、自动任务又共用同一套提示词和工具面。结果是：

- 用户以为在聊天，系统却在派活；
- 纯聊天可能启动浏览器；
- 任务被塞进聊天消息流，任务详情和聊天记录混在一起；
- 自动任务和页面派活各写一套台账。

产品负责人的明确要求：

- 首页发送默认进入一个新会话；
- 聊天就是聊天，不要和任务扯在一起；
- 任务要有明确的工作流、状态和边界。

## 决策

1. **Conversation 只负责对话**：理解、澄清、规划、提出任务卡。
2. **Task 只负责执行**：目标、输入、产出、约束、角色、状态、审批点。
3. **首页发送 = 创建新会话**；不创建 Task，不启动浏览器。
4. **派活 = 显式任务卡确认**：用户在聊天中确认，或在页面显式创建。
5. **任务详情独立于聊天**：任务过程用 TaskEvent 时间线展示，不塞进消息流。
6. **Automation 只创建 Task**：到点执行和“马上跑”都走同一 TaskService。
7. **BrowserSession 只在任务需要时申请**：纯聊天不挂浏览器工具。

## 后果

正面：

- 首页行为符合用户直觉；
- 聊天和任务的提示词、工具、数据彻底分开；
- 任务可以独立追踪、取消、重试、审批；
- 自动任务和派活共用一套台账。

代价：

- 需要新增 Task/Approval/TaskEvent 数据模型；
- 需要改首页、聊天页、侧栏和任务详情；
- 需要把现有 `tasks.dispatch` 从首页移除；
- 旧任务数据需要迁移。

## 不采用的方案

- **继续在聊天页里嵌任务视图**：无法表达任务状态、审批和产物，且会让聊天越来越重。
- **首页发送后让 AI 自己决定聊天还是任务**：不可预测，容易再次越权启动浏览器。
- **自动任务继续单独一套记录**：会造成状态不一致和重复实现。

## 验收

- C-01、C-02、T-01、T-02、A-01、A-02、R-03；
- 纯聊天无 BrowserSession；
- 任务详情独立页面；
- 自动任务与派活同列表。
