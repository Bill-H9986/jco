# ADR-0002：通用发布工作流 + 平台适配层

- 日期：2026-10-16
- 状态：已采纳（2026-10-16 随 M1 设计冻结拍板通过）
- 来源：产品负责人指示——"发布工作流难道不是一个通用工作流吗？所有的平台都用这一个工作流！至于各平台的细微差别和规则这是 AI 的事与发布工作流无关吧！"
- 关联：M1 技术方案 · 第一节（引擎 / 适配层边界）

## 背景

M1 设计初版以"抖音发布助手"为表述对象。产品负责人指出：发布工作流应当**通用化**——所有平台共用同一条工作流，平台差异不应带进工作流本身。

## 决策

采用 **"通用引擎 + 平台适配层"** 架构：

1. **工作流（引擎）= 通用**：任务管理、浏览器生命周期、状态机、协议、界面、契约——**写一次**，所有平台复用；
2. **平台差异 = 适配包**：`app/publish/platforms/<平台>/`（adapter + selectors + rules），**每平台一个小目录**；
3. **平台规则分两档处理**：
   - 硬规则（标题字数 / 话题数量 / 视频规格）→ 写进**规则卡**（rules.json），文案生成与界面提示自动读取——可测、可更新；
   - 软规则（内容合规、风格适配）→ 由内核 AI 在生成文案时把握。

## 对"规则是 AI 的事"的补充说明（属于本决策的一部分）

- 工作流骨架确实与平台无关——这一点产品负责人理解正确；
- 但"硬规则"若完全交给 AI 临场把握，会**不可测、易漂移**；放进规则卡后，AI 生成时自动引用、用户可改——规则明确、责任清楚；
- 因此落地形态是："**工作流通用 + 规则卡明确 + 软规则交 AI**"，三者各归其位。

## 后果

- 正面：新增平台成本 = 一个适配包 + 一次真站验收；界面 / 契约 / 测试全部复用；
- 风险：适配接口在抖音实测中可能需微调——调整走变更单；等 2–3 个平台接入后接口趋于稳定；
- **顺序纪律**：先跑通抖音（第一个适配包），再批量接入其他平台——避免把多平台设计都押在未实测的接口上（防返工）。
