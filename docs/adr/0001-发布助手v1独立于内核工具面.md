# ADR-0001：发布助手 v1 独立于内核工具面

- 日期：2026-10-16
- 状态：待拍板（随 M1 设计冻结一并评审）
- 关联：M1 发布插件（抖音）技术方案 第二节

## 背景

J.Co 以 DSH 为 Agent 内核，长期方向是"员工=插件、工具面按角色挂载"（发布=浏览器工具）。
M1 的第一个员工（抖音发布助手）面临选择：v1 直接做成内核工具面挂载，还是先独立实现？

## 决策

**v1 采用独立子进程架构（Playwright + 系统 Edge），不接入内核工具面。**

## 理由

1. **v1 是确定性流程**（打开 → 上传 → 填写 → 停在发布前），无需模型自主决策，独立实现更直接；
2. **降低风险面**：内核工具面挂载涉及插件开发、权限面与协议；刚完成工具面收口（jco-chat.patch.yml），不宜立即反复；
3. **符合"最小可用"纪律**：先跑通一个平台的最小闭环，平台适配独立演进；
4. **可控回退**：独立进程可随时停、可单独测试，失败不牵连内核。

## 后果

- 正面：M2 施工面小、验证快；多平台扩展只需新增适配目录；
- 反面：v2 收编内核工具面时需要一次重构（把助手能力包装成工具）——已在技术方案中预留路径；
- 中性：界面呈现不变（用户看到的是"发布员工在干活"，与实现架构无关）。
