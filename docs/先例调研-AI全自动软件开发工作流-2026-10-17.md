# 先例调研：AI 全自动软件开发工作流

- 日期：2026-10-17
- 目的：为 J.Co 的 AI 全自动开发工作流 v1.6 提供最新外部依据，避免只凭经验定流程。
- 结论：AI 全自动开发必须有**自主等级、上下文工程、评估集、反馈传感器、成本上限和安全门**；不能把“模型能生成代码”当成“项目能自动交付”。

---

## 一、DORA 2025：AI 是放大器，不是替代品

出处：https://dora.dev/research/2025/dora-report/

关键结论：

- AI 的主要作用是**放大组织已有的优势和问题**；
- 最大的回报来自底层组织系统、平台和流程，而不是工具本身；
- 只按“生成了多少代码”衡量生产力会误导；
- 应看交付流动和稳定性：lead time、部署频率、变更失败率、rework rate（返工率）。

对 J.Co 的吸收：

- 不用“AI 写了多少行/多少文件”当进度；
- 每个工作单元记录：开始/完成时间、返工次数、失败次数、安装版是否通过；
- 返工率是核心质量指标：交付后被用户抓出的同类问题，必须回到流程找根因；
- 平台/门禁/模板先做好，再谈全自动。

## 二、METR：真实任务里 AI 可能让人变慢

出处：https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/

关键结论：

- 2025 年的一项随机对照试验中，有经验的开发者在真实开源仓库任务上使用 AI 反而 **慢 19%**；
- 开发者主观以为 AI 让自己快 20%，说明“感觉快”不可靠；
- 基准测试（如 SWE-bench）和真实项目有差距：真实任务需要上下文、风格、测试、文档和人工判断。

对 J.Co 的吸收：

- 不拿公开 benchmark 分数当项目验收；
- 以真实仓库任务、真实安装版、真实用户动线为准；
- 每个工作单元必须记录真实耗时、返工和失败；
- AI 生成的“看起来完成”必须有可运行检查。

## 三、12-Factor Agents：Agent 要像软件一样可控

出处：https://github.com/humanlayer/12-factor-agents

关键因子：

1. 自然语言 → 工具调用；
2. 自己拥有 prompts；
3. 自己拥有 context window；
4. 工具是结构化输出；
5. 统一执行状态和业务状态；
6. 用简单 API 支持启动/暂停/恢复；
7. 用工具调用联系人类；
8. 自己拥有 control flow；
9. 把错误压缩进上下文；
10. 小而专注的 Agent；
11. 从任何入口触发；
12. 把 Agent 做成无状态 reducer。

对 J.Co 的吸收：

- 任务状态和业务状态统一进 store，不靠页面内存；
- 任务可暂停/恢复/取消，审批用结构化 Approval；
- 错误摘要进 TaskEvent，不把整段原始日志塞回模型；
- 聊天、发布、运营、后期是不同小 Agent，不做万能大 Agent；
- 不让模型完全接管 control flow；波次、依赖、门禁由软件控制。

## 四、Microsoft：从最低复杂度开始

出处：https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns

关键结论：

- 先判断是否真的需要 Agent；能用一次模型调用解决就不要上 Agent；
- 单 Agent + 工具通常是企业默认；
- 多 Agent 只在跨域、不同安全边界、需要并行 specialization 时使用；
- 多 Agent 增加协调、延迟和失败模式；
- 要设置迭代上限，防止工具调用死循环。

对 J.Co 的吸收：

- 先用单 Agent + 明确工具白名单；
- 不因为“看起来高级”就上多 Agent；
- 发布、运营、后期按角色拆，是因为安全边界和工具不同，不是为了堆 Agent；
- 每个任务设置最大工具调用次数、超时和成本上限。

## 五、Thoughtworks Radar：上下文工程与反馈传感器

出处：

- https://www.thoughtworks.com/radar/techniques/agentic-coding
- https://www.thoughtworks.com/radar/techniques/context-engineering

关键结论：

- 上下文要动态、精确管理，不能把一堆文档全塞给模型；
- 渐进式上下文披露，按任务加载需要的说明；
- 团队应维护 curated shared instructions（AGENTS.md/工作流），不让每个人从零写 prompt；
- coding agent 需要 feedback sensors：编译器、lint、结构测试、测试套件、浏览器测试；
- 用 DORA 指标和返工率衡量，不按生成代码量；
- Agent 默认按零信任、最小权限设计。

对 J.Co 的吸收：

- 每个工作单元只加载相关文档：工作队列 + 对应层文档 + 测试命令；
- 不把全部 M11 文档每轮灌进模型；
- 把 AGENTS.md、工作流、M11 设计包作为共享指令；
- D0–D4、typecheck、Biome、单测、E2E、视觉、安装冒烟都是 feedback sensors；
- 工具权限按零信任和最小权限设计。

## 六、OWASP LLM Top 10：Agent 安全门

出处：https://genai.owasp.org/llm-top-10/

2025 风险清单：

1. Prompt Injection；
2. Sensitive Information Disclosure；
3. Supply Chain；
4. Data and Model Poisoning；
5. Improper Output Handling；
6. Excessive Agency；
7. System Prompt Leakage；
8. Vector and Embedding Weaknesses；
9. Misinformation；
10. Unbounded Consumption。

对 J.Co 的吸收：

- 外部网页/评论/文件名按“资料”处理，不按指令；
- 工具最小权限，聊天不挂浏览器/文件写入；
- 发布、删除、支付必须 Approval；
- 模型输出不直接当命令执行；
- 不把系统提示词、密钥、登录态写进日志；
- 限制 token、工具调用次数、重试次数、任务时长；
- 第三方技能/插件必须审查来源和权限。

## 七、SWE-bench：基准不是项目验收

出处：https://www.swebench.com/

关键结论：

- SWE-bench 用真实 GitHub issue 评测，但仍然是基准，不等于真实产品交付；
- 有 Verified/Lite/Multilingual/Multimodal 等子集，说明不同任务形态差异很大；
- 评测结果常用于比较模型/agent，不直接代表你的项目能自动维护。

对 J.Co 的吸收：

- 建自己的 J.Co Agent Eval：20–30 个真实任务，覆盖页面、内核、数据、工具、安装；
- 评测指标：是否通过、工具调用次数、耗时、成本、返工、人工介入次数；
- 不用公开 leaderboard 分数替代安装版验收。

## 八、Anthropic / Spec Kit / Addy Osmani：已有结论继续保留

- Anthropic《Building Effective Agents》：workflow 优先、简单优先、透明、工具设计清楚；
- GitHub Spec Kit：Specify → Plan → Tasks → Implement，每个任务小到可测试；
- Addy Osmani《The 70% problem》：AI 快速做到 70%，最后 30% 靠验证、工艺和人的判断；
- Simon Willison：不能解释的代码不提交；
- Playwright：视觉回归是 UI 细节的 feedback sensor。

## 九、v1.5 的缺口与 v1.6 的升级

| v1.5 缺口 | v1.6 升级 |
|---|---|
| 没有明确自主等级 | 新增 L0–L4 自主等级；高风险动作永远 L2 以下 |
| 没有项目级 Agent 评估集 | 新增 J.Co Agent Eval（真实任务、通过率、工具调用、耗时、成本、返工） |
| 上下文容易堆太多 | 新增 Context Pack：每个工作单元只加载相关文档 |
| 没有成本/迭代上限 | 新增 token、工具调用、重试、任务时长上限 |
| 安全门不成体系 | 新增 OWASP LLM Top 10 对照门 |
| 只看功能完成 | 新增 DORA 风格指标与返工率 |
| 单/多 Agent 选择没有规则 | 新增“最低复杂度”与“小 Agent”原则 |
| 工作队列只有功能单元 | 新增 W0-07 Agent Eval 与反馈传感器单元 |

## 十、结论

v1.6 的核心不是“让 AI 更自由”，而是：

```text
更小的自主范围
  + 更清楚的上下文
  + 更硬的反馈传感器
  + 更明确的停手/审批点
  + 更真实的项目评估
  + 更低的成本和权限上限
```

这才是能用于 J.Co 这种真实项目的全自动开发工作流。
