# 先例调研：创作后台任务与状态恢复

- 日期：2026-10-20
- 触发问题：创作页生成中切换到其他页面，iframe 被销毁，页面内循环和进度一起丢失
- 结论：长任务放主进程，页面只负责发起和重连；任务状态持久化，结果每步落盘

## 查到的关键事实

### Electron 进程与生命周期

- Electron 主进程是 Node.js 环境，负责窗口和应用生命周期；每个 BrowserWindow 有独立渲染进程；窗口销毁时对应渲染进程终止。
- 渲染进程里的异步循环不适合承载长任务：页面切换、iframe 导航、刷新或崩溃都会让循环消失。
- `ipcMain.handle` + `ipcRenderer.invoke` 适合“发命令拿回执”，主进程可用 `webContents.send` 推送任务事件；`contextBridge` 只暴露受控 API。
- `utilityProcess` 可创建带 Node.js 和 MessagePort 的子进程，适合 CPU 密集型任务；本项目的图片/视频生成主要是网络 I/O，放主进程异步执行即可，后续需要 CPU 转码再拆 utility process。
- `powerSaveBlocker.start('prevent-app-suspension')` 可用于长任务期间阻止系统挂起，任务结束必须 stop。

### 后台任务恢复

- Azure 架构中心的后台任务规范要求：后台任务必须能优雅处理重启；长任务/多步任务要把任务状态持久化做 checkpoint；重复执行要幂等，避免重复产出或覆盖。
- Temporal 的 durable execution 通过事件历史记录每一步，失败后从最后一个事件恢复；关键是状态、进度、已完成步骤和下一待执行步骤都不能只存在内存里。
- AWS Builders' Library 的 retry 规范：远程调用要有超时、重试、退避和 jitter；有副作用的调用必须幂等，不能因为超时就把“可能已成功”的结果当失败重做。

## 对本项目的方案

### 不采用

- 不把长循环留在页面里，也不依赖 `beforeunload` 抢救；页面销毁时异步回调已不可靠。
- 不只用 localStorage 记进度；它只适合轻量 UI 偏好，不适合承载任务状态和结果文件。
- 不把 WebContentsView 常驻页面作为主方案；它能减少切页销毁，但不能解决应用重启和崩溃恢复。

### 采用

1. 主进程新增 `media-jobs` 服务：图片、视频生成循环在主进程执行，任务 JSON 持久化到 kernel 数据目录。
2. 每个任务记录 `id / kind / draftId / status / progress / stepText / items / providerTaskId / createdAt / updatedAt`。
3. 页面通过 `media:job:start` 发起，主进程用 `media:job` 事件推送状态；页面用 `media:job:get/list` 轮询兜底。
4. 主进程每完成一张图或一段视频就写回草稿并保存任务 JSON，页面切走不中断。
5. 页面记住最后打开的草稿 id；回来先恢复该草稿，再挂上正在跑的任务。
6. 应用重启时，未完成任务标为“已中断”，保留已完成结果和供应商任务号；能继续轮询的继续，不能继续的显示重试。
7. 所有重复执行以 `draftId + index` 去重，已完成的图片/视频不重复生成；重试只重做未完成项。
8. 任务运行期间显示明确工作态：草稿卡进度、任务步骤、每段状态、可停止入口。

## 验收要求

- 生成中切到其他页面，再回创作页，任务仍在跑且进度继续更新。
- 生成中刷新创作页，任务仍可重连并显示进度/已完成结果。
- 关闭应用再启动，未完成任务显示“已中断”，已完成结果保留，可重试。
- 两个生成任务不会重复写同一图片/视频索引。
- 任务失败不会把草稿清空，失败项可单独重试。
