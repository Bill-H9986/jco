> **本文件是 J.Co 项目全部开发活动的唯一流程依据。**
> 无论开发由人还是 AI 执行：**动工前必读，执行中必遵。**
> 
> 建立目的（产品负责人原话）：**"以防后续时间久了，代码量大了，容易跑偏。"**

## 一、总则

### 1.1 这份标准治什么病（全部为真实发生过的教训）

| 历史教训 | 根因 | 本标准的对策 |
|---|---|---|
| 前端页面先做、设计数值后定，全站返工对齐（18 轮） | 标准后置（先施工后立标） | 铁律 1：设计冻结制 |
| 图标消失、灰块打架、输入台歪斜等问题靠人眼才发现 | 质量靠人查，没有自动拦网 | 铁律 3：机器门禁 |
| "输入台统一""助手球归位"等调整随时插队，碎步推进 | 变更无制度 | 铁律 4：变更不插队 |
| 12 个页面各抄一份样式，改一处要改 12 处 | 没有单一来源 | 第五章：单一来源纪律 |
| 把"发布本职步骤"（封面 / 合集 / 声明 / 位置等）误标为"不该管"，导致交付残缺（2026-10-16 产品负责人纠正） | 职责边界定义错误（把该干的划进了禁区） | 每个任务的"**完整职责清单**"必须先定义清楚；"不该管"仅指任务之外 |

### 1.2 八条铁律

1. **无调研与设计不开工** —— 先例调研（业界资料 / 官方文档 / 开源项目，能抄就抄，产出《先例调研笔记》）与设计包未完成并冻结（附录 B）之前，不写功能代码。
2. **无断言不接活** —— 每个模块动工前，先写出"此刻会失败"的验收用例。
3. **机器说了算** —— 门禁全绿才允许进入下一步；人眼只做最终体验验收。
4. **变更不插队** —— 任何新想法、新调整，登记变更单（附录 C），里程碑封版后统一排期；中途只有致命缺陷允许走 Hotfix 快捷线。
5. **封版即存档** —— 每次封版必须同时完成：git tag + CHANGELOG + 存档 zip，三重回滚保险。
6. **全站一体（v1.3 新增）** —— 共享组件/全站性改动（侧栏、按钮、样式、导航、会话等）**一次改齐全部页面（只改一页 = 未完成）**；产品目录（`设计原型\`）只放产品文件，**验证副本与临时产物一律放开发工作区**；每批完成必须**打包并装机**后才算交付。以上三条全部由机器门禁拦截——`npm run gate` 内置「全站一致性审计」（`app\scripts\audit-frontend.mjs`）。
7. **细节必须清单化、断言化、证据化（v1.4 新增）** —— 细节不能靠“AI 再仔细一点”或人眼兜底：每个 UI/交互任务必须有 D0 设计契约、D1 状态矩阵、D2 自动检查、D3 独立审查、D4 交付证据；没有细节清单和截图/回归证据的改动，不得称为完成。详见 [`细节工程与AI开发门禁-2026-10-17.md`](细节工程与AI开发门禁-2026-10-17.md)。
8. **全软件分层验收（v1.5 新增）** —— 不是只做前端、也不是只做页面：主进程、领域/应用层、DSH 内核、提示词、工具权限、浏览器会话、ffmpeg、数据迁移、IPC、安装/升级/回滚、安全、测试、日志、文档全部纳入 [`全项目迁移总表`](plans/M11-任务会话重构/全项目迁移总表.md)。任何一层未 `verified`，不得说“整个项目完成”。

### 1.3 分工（谁负责什么）

| 角色 | 负责 | 不负责 |
|---|---|---|
| **产品负责人（Jay）** | 提需求、使用软件、验收"好不好用" | 不评审技术方案、不评审流程细节、不选工具 |
| **执行者（AI 会话 / 工程师）** | 设计、编码、测试、文档、交付、留痕 | —— |

**产品负责人只在三个时刻出场**：

1. **立项**——"我要做什么"（一句话即可）；
2. **验收**——东西做出来，打开用一下，说"行 / 不行"；
3. **变更**——攒着的新想法统一提（走变更单）。

技术选择、工具选型、流程细节，一律由执行者按本标准决定并执行，不拿来问产品负责人。

## 二、开发流水线

```
立项 → 先例调研 → 设计（冻结） → 施工 → 验收 → 交付 → 运维（反馈回流到立项）
```

### 2.1 立项

- **入口**：产品负责人一句话需求 / 运维反馈的缺陷
- **动作**：填写《里程碑立项单》（附录 A）——必须写明：目标、范围、**明确不做什么**、验收标准（"能演示 XXX"此类可检验的句子）
- **出口**：立项单确认 → 进入设计
- **纪律**：同一时间只有一个活跃里程碑；其余想法一律进 backlog（登记不丢）

### 2.2 调研与设计（冻结制）

**第 0 步 · 先例调研（强制，2026-10-16 新增）**：

- 产品负责人指示原话："开发之前要先去网上找一遍相应的资料、文档、项目啥的……人家前辈给我们做好了一切！我们照抄就行！节省了大量时间还避免了自己写的一堆 BUG！"
- 动手设计前，必须先检索**业界资料 / 官方文档 / 开源项目 / 最佳实践**；
- 产出 **《先例调研笔记》**：找什么 → 找到什么（附出处）→ **抄什么、怎么适配进 J.Co** → 哪些不抄、为什么；
- **没有调研笔记，不进入设计**——"能抄就抄"是纪律，不是选修（参照项目已立的 OpenOPC 借鉴模式）。

**第 1 步 · 设计四件套**（放 `docs\plans\<里程碑名>\`）：

  1. **PRD**：背景 / 范围 / 用户流程 / 红线 / 验收标准
  2. **技术方案**：架构 / 模块清单 / 数据流 / 风险与降级预案
  3. **接口契约**：工具面 schema / IPC 清单 / 数据结构 / 错误码
  4. **E2E 验收用例骨架**：先写"会失败"的测试
- **出口**：设计冻结评审通过 → 冻结版本锁定，施工期间只走变更单
- **纪律**：设计期间不写功能代码

### 2.3 施工

- **唯一队列**：`docs\plans\M11-任务会话重构\工作队列.md`；同一时刻只允许一个 `in_progress`。
- **工作单元卡**：每个单元必须写清：层、页面/模块、依赖、验收、证据、回滚；没有卡的活不开工。
- **方式**：先写“此刻会失败”的测试，再做最小实现；先目标测试，再全量门禁。
- **分层门禁**：
  - UI：D0–D4 细节门禁 + 视觉回归；
  - 数据：迁移/回读/备份/恢复；
  - 内核：profile 工具白名单/真实内核冒烟；
  - 工具：浏览器/ffmpeg 真实冒烟；
  - 安装：打包 + 装机 + 卸载/回滚。
- **提交**：Conventional Commits（见 4.2）；一个工作单元一个提交，提交说明附验证结果。
- **出口门禁**：目标测试 + `npm run gate` + 对应层门禁全绿。
- **纪律**：不跨波次跳做；不私自扩大范围；发现契约有坑 → 走变更单，不硬改。

### 2.4 验收

- **机器验收**：全量 E2E 回归 + 真机冒烟
- **收敛检查（v1.2 新增 · 源自 Spec Kit 的 converge）**：对照设计冻结包的验收标准**逐条核对验证证据**——每一条都要说清"怎么验的、结果如何"；**没有验证证据的条目 = 未收敛，不得交付**
- **人工验收**：产品负责人真机点验，只评"好不好用"
- **出口**：通过 → 交付；不通过 → 缺陷单回施工
- **纪律**：不带着已知问题交付

### 2.5 交付

- **对抗审查（v1.2 新增 · 源自 Claude Code 实践的 adversarial review）**：封版前，用**独立视角**（另一 AI 会话或专门角色）对着设计规范专门"挑刺"——找漏掉的边界、没验的场景、说不通的设计；发现的问题修复或登记后，方可封版
- **封版三件套**：git tag（SemVer 版本号）+ CHANGELOG（自动生成）+ 存档 zip
- 逐项勾选《封版清单》（附录 D）
- 更新 `README.md` 里程碑时间线（只追加，不涂改）

### 2.6 运维（反馈回流）

- 缺陷 / 建议 → 登记 → 进入下一个立项
- **缺陷处理三分离（v1.2 改 · 源自 Spec Kit 的 bug fixing）**：评估（定位根因，写出复现步骤）→ 修复 → **验证（回到原始症状复现确认）**——"没有验证不算修好"
- **紧急缺陷走 Hotfix 快捷线**：评估 → 修复 → 验证 → 补丁版本号 → CHANGELOG 补记

### 2.7 全自动执行协议（v1.5 新增）

AI 全自动开发不是“想到哪做到哪”，而是固定循环：

```text
1. 读事实：项目现状 / M11 总表 / 迁移矩阵 / 工作队列 / 当前门禁
2. 选单元：队列里第一个 pending 且依赖 verified 的工作单元
3. 写失败测试（先红）
4. 最小实现（只做该单元）
5. 跑目标测试
6. 跑 npm run gate
7. 跑该层门禁（UI D0–D4 / 数据迁移 / 内核工具 / 真机 / 安装）
8. 收证据（截图、日志、命令结果、迁移对比）
9. 更新工作队列、迁移矩阵、风险清单、ADR/文档
10. 提交一个 Conventional Commit，进入下一个单元
```

硬规则：

- **WIP=1**：没有完成当前单元，不开始下一个。
- **不跳层**：页面依赖的数据/契约没通过，不允许先改页面。
- **不跳波次**：Wave 0 未通过，不进入 Wave 1。
- **不接受口头完成**：必须附命令结果、截图或真实产物。
- **不掩盖失败**：失败进 `blocked` 或缺陷单，不把门禁改成通过。
- **不只改前端**：任何工作单元必须写明对主进程/内核/数据/工具/安装的影响。
- **不全站同时大爆炸**：按波次替换旧实现，但每一波都必须保持整个应用可用。

停手条件：

- 需要产品负责人拍板交互/范围；
- 需要真实平台登录扫码；
- 环境缺依赖且无法在本机修复；
- 门禁失败但根因不在当前工作单元；
- 发现安全问题需要单独设计。

停手时登记到工作队列的 `blocked` 和待用户清单，不假装完成。

## 三、质量门禁（机器把关）

### 3.1 门禁清单

| # | 检查项 | 工具 | 触发时机 |
|---|---|---|---|
| 1 | 类型检查 | TypeScript ◆ | 每次 |
| 2 | 代码规范 | Biome ◆ | 每次 |
| 3 | 单元测试 | Vitest ◆ | 每次 |
| 4 | 端到端回归 | Playwright Test（Electron 模式）◆ | 每次 |
| 5 | 前端结构检查 | preflight（design-taste 技能包） | 改动页面时 |
| 6 | 视觉守门员 | verify-computed（逐元素比对） | 改动样式时 |
| 7 | 真机冒烟 | Electron 实机跑核心动线 | 封版前 |

◆ = M0 工程地基建设内容（见第八章）；5、6 为既有资产，纳入统一门禁。

### 3.2 红线

- `npm run gate` **一条命令全绿，是推进的唯一标准**；
- 任何豁免必须写入提交说明并说明理由；
- 门禁不绿 = 不合格产物，**禁止交付到产品负责人面前**。

### 3.3 细节门禁（v1.4 新增）

`npm run gate` 证明的是工程基线，不自动证明“细节好用”。任何 UI、交互、文案、消息排版、任务详情、空态/错误态改动，还必须过 D0–D4：

| 门 | 内容 | 不通过会怎样 |
|---|---|---|
| **D0 设计契约** | 参考截图/线框、design token、组件状态矩阵、文案表、响应式规则、深浅色规则、非目标 | 不允许开始实现 |
| **D1 实现契约** | 输入输出、default/hover/focus/active/disabled/loading/empty/error、长文本/空数据/特殊字符/网络失败、键盘与焦点 | 任务卡不完整，不允许开工 |
| **D2 自动检查** | typecheck、lint、单元测试、视觉回归、几何断言、文本/数据快照、可访问性扫描、长文本/窄窗口/深浅色、安装版冒烟 | 机器不绿，不允许交付 |
| **D3 独立审查** | AI 自审清单、另一个 AI 会话对抗审查、产品负责人只用可见信息走查 | 审查未完成，不允许封版 |
| **D4 交付证据** | 改动前后截图/录屏、视觉回归结果、关键状态截图、已知差异、未解决项 | 没有证据，只能叫“实现了一部分” |

**细节资产（必须沉淀，不能每次现猜）：**

- 设计 token：字号、行高、间距、圆角、颜色、阴影；
- 组件状态矩阵；
- 文案表与术语表；
- 真实数据样本：长文本、空数据、超长标题、特殊字符、慢加载；
- 视觉基准截图；
- 已知取舍和未解决项。

**AI 开发验证回路：**

1. 先给规范、参考图、约束和验收标准，不让 AI 凭感觉；
2. 让 AI 先产出细节清单和会失败的验收用例；
3. 小步实现，每步截图对比 + 跑检查；
4. 要求 AI 展示证据，不接受“已完成”口头结论；
5. 另一个会话做对抗审查；
6. 产品负责人按普通用户视角最终验收。

完整分类、检查矩阵、提示词模板和聊天消息样例见 [`细节工程与AI开发门禁-2026-10-17.md`](细节工程与AI开发门禁-2026-10-17.md)；具体任务直接复制 [`细节任务卡模板.md`](细节任务卡模板.md)。

### 3.4 全项目门禁（v1.5 新增）

`npm run gate` 是工程基线，不等于全项目验收。M11 还必须逐步纳入：

| 门禁 | 作用 |
|---|---|
| `check:no-direct-business-localstorage` | 业务页面不得直接读写旧 `jco-*` 业务 key |
| `check:no-hardcoded-industry` | 系统提示词、页面示例、默认任务不得写死行业 |
| `check:no-chat-browser-tools` | chat profile 不得挂浏览器/编辑/文件写入工具 |
| `check:no-direct-tasks-dispatch` | 页面不得直接派活，必须走 TaskService |
| `check:no-duplicate-sidebar` | 页面不得再复制侧栏/助手球/输入台 |
| `check:no-message-truncation` | 消息落盘/回读不得截断 |
| `check:all-pages-migrated` | 16 个现有页面 + 新任务详情全部 `verified` |
| `check:full-project-layers` | 全项目迁移总表所有层 `verified` |
| `check:cross-page-journeys` | 跨页旅程 E2E |
| `check:visual-regression-all` | 全站关键状态视觉基准 |

任何一项未实现前，工作流中对应单元只能是 `pending` 或 `in_progress`，不能标 `verified`。

## 四、版本与变更管理

### 4.1 分支模型（GitHub Flow）

- `master`：主干，始终可用；
- `feat/xxx`、`fix/xxx`：短分支开发，完成即合回主干；
- `tag`：`vX.Y.Z`，与每次封版一一对应。

### 4.2 提交规范（Conventional Commits）

格式：`type(scope): 描述`

type ∈ `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`

### 4.3 版本号（SemVer）

- 0.x 阶段规则：加功能 → +0.1.0；修缺陷 → +0.0.1；
- CHANGELOG 由工具自动生成（commit-and-tag-version），不手写。

### 4.4 变更单制度

- 设计冻结之后的一切改动，必须走变更单（附录 C）；
- 默认处理：进 backlog，封版后统一排期；
- 只有"致命缺陷"允许立即插队（Hotfix 线）；
- 产品负责人的新想法同样登记，**不打断当前里程碑**。

### 4.5 存档体系（继承现有三层保险）

- 存档 zip：`备份\存档-<里程碑>-<日期>.zip`
- 回滚说明：`备份\回滚说明-<里程碑>-<日期>.md`
- 加上 git tag，三重回滚保险，任何一步都能退回去。

### 4.6 工作队列与状态（v1.5 新增）

- 唯一队列：`docs\plans\M11-任务会话重构\工作队列.md`；
- 状态：`pending` / `in_progress` / `blocked` / `verified`；
- 同一时刻只允许一个 `in_progress`；
- 只有依赖全部 `verified` 的 `pending` 单元才能被选中；
- 完成必须同时更新：工作队列、全站迁移矩阵、全项目迁移总表、风险清单、相关 ADR/文档；
- 工作单元不能因为“做起来麻烦”被跳过；只能因为外部阻塞进 `blocked`；
- 队列顺序变更必须走变更单，不能施工中随手改。

## 五、防跑偏机制（长期纪律核心）

时间久了、代码量大了，最怕四样东西跑偏。对应四道栓：

### 5.1 单一来源纪律（防来源分裂）

- 样式：全站只从 `设计原型\assets\jco-ui.css` 取零件；
- 细节资产：design token、组件状态矩阵、文案表、视觉基准截图只保留一份；
- 事实数据：只从一个数据层读；
- 同一逻辑：只写一处；
- **一旦发现"第二份"，立即合并——禁止并行演化。**

### 5.2 开工仪式（防标准散失）

每个新开发会话 / 新成员开工前：

1. 读 `AGENTS.md`（项目根 · 编码准则：三硬约束 + 编码四原则）→ 读 `README.md` → 读本标准 → 读当前里程碑设计包；
2. 第一件事：跑一次全量门禁，确认基线是绿的；
3. 然后才能动手写任何代码。

### 5.3 定期体检（防质量滑坡）

- 每次封版：全量回归 + 视觉守门员；
- 结构性健康检查：preflight 0 违规。

### 5.4 变更留痕（防方向漂移）

- 所有变更单、ADR（架构决策记录）、复盘记录在案；
- 里程碑时间线只追加、不涂改——历史可追溯。
