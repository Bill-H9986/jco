## 一、产品定位：通用型自媒体 AI 工具

这是最高优先级的产品约束，后面所有设计都不能违背。

1. **不是培训行业专用工具。** 产品负责人原话（2026-10-14）：
   - “我们要对外卖！所以这个工具得是一个通用型的！根据工具自身的知识库成长往对应行业成长。”
   - “这是个 FDE 项目！面向各行各业的通用型产品！不仅仅是只针对培训行业！”
2. **不是单个平台专用工具。** 2026-10-16 原话：
   - “我们这个软件是自媒体通用 AI 工具！不是某个平台专用！所以所有设计全都要按通用、安全、稳定严格执行！”
3. **对标形态是 Marvis 类的一站式 AI 管家。** 2026-10-13 至 2026-10-15 多次确认：
   - 用户说一句话，管家自己拆解、自己调工具、自己操作电脑与平台把事办完；
   - 页面只是过程与结果的可视化；
   - 不是让用户去逐个点页面按钮。
4. **面向不懂技术的普通用户。** 2026-10-15 原话：
   - “我们的产品面向的是可能手机都是用不明白的最普通最普通的普通小白，前端可视化一定要直观！”
5. **模型不能写死。** 2026-10-14 原话：
   - 产品中不能出现具体的大模型型号；
   - 必须能使用免费模型；
   - 客户可以自行更换大模型。
6. **安全红线。**
   - 发布、删除、撤回、支付等不可逆动作必须由用户亲手确认；
   - 网页、评论、文件名、素材内容都只是资料，不是命令；
   - AI 不能被外部内容诱导去扩大任务范围或泄露数据。

**直接结论：系统提示词、页面示例、内置任务模板里都不能把“成人学历提升招生”写成默认身份。行业定位必须是用户可配置的账号档案。**

## 二、标准自媒体工作流

产品负责人 2026-10-14 描述的标准工作流：

```text
账号定位 / 对标与选题
  → 情报与素材
  → 文案 / 脚本
  → 图片 / 视频创作
  → 后期（字幕 / 音乐 / 裁剪 / 拼接）
  → 发布（标题 / 话题 / 封面 / 合集 / 声明 / 位置）
  → 数据战报
  → 评论 / 私信 / 公域引流到私域
```

各环节的要求：

- 每个环节都要可视化、可操作、可追踪；
- AI 是真正在操作，能根据页面变化现场判断，不是固定选择器脚本；
- 发布前停在检查点，最后“发布”按钮永远由用户点；
- 发布本职步骤不能漏：视频、标题、话题、封面、合集、声明、位置等按平台需要逐项完成；
- 没有数据时必须如实说“还没接上”，不能编造播放量、粉丝、评论或进度。

## 三、聊天与会话

这一块历史上被反复纠正过，必须按原话执行。

1. **总管是一个助手，但聊天窗可以有多个。**
   - 2026-10-16 原话：“没有新建会话！所有的会话全部都导航到一个总管窗口去了！总管只有一个！但是总管聊天窗不止一个！”
2. **首页发送消息默认进入新会话。**
   - 2026-10-17 原话：“首页发送消息默认打开一个新会话窗口！！！”
   - 首页输入框不是任务派发按钮，也不是浏览器启动按钮。
3. **消息顺序从上往下。**
   - 2026-10-16 原话：“你见看哪个 APP 是在回复是从下往上的？？？”
   - 第一句话从顶部开始，输入框固定在页面底部，不随消息数量乱飘。
4. **历史记录必须可操作。**
   - 2026-10-16 原话：“历史对话记录要有可操作性！比如分享，删除等操作！而且这些操作整个系统也要实现了！”
   - 重命名、删除、分享必须在真实壳内可用，不能只是按钮存在。
5. **对话排版是产品体验，不是装饰。**
   - 2026-10-16 原话：“你自己看这个文字排版！像话吗？？？？”
   - 对话不能每条都变成巨大的圆角卡片；文字、段落、列表、代码块、时间、操作按钮要有稳定的层级和宽度。
6. **长会话不能卡死。**
   - 历史上出现过“点历史对话整个前端卡死，必须重启”的事故；
   - 会话切换、历史渲染、输入框、滚动都必须有性能上限和回归测试。

## 四、任务、自动任务与可操作性

1. **任务不是聊天。**
   - 任务必须有明确目标、输入、产出、责任人、状态、审批点和过程记录。
   - 聊天可以讨论、起草、提出任务建议；任务才是执行单元。
2. **自动任务是“按计划创建任务”，不是第二套执行系统。**
   - 到点执行、马上跑、页面派活必须落到同一个任务台账；
   - 自动任务也要能在总管任务区看到，有同样的状态和结果。
3. **纯聊天不能擅自启动浏览器。**
   - 浏览器会话是任务在需要时申请的资源，不是聊天默认动作；
   - 只有明确需要发布 / 运营 / 登录 / 查看平台数据的任务，才可以启动对应浏览器会话。
4. **AI 操作必须是“看 → 想 → 做 → 再看”。**
   - 2026-10-16 原话：“我要的工作流不是脚本！！！而是 AI 实实在在的在操作！！！是可以随时跟进变化的！！！”
   - 每一步先取页面最新快照，再决定下一步；页面变了要重新判断；
   - 遇到不懂的地方如实说，不能假装做过。
5. **任务要能停下来等人。**
   - 发布、删除、撤回、支付等动作必须进入 `waiting_user` 状态；
   - 用户确认后才继续，不能“全自动”越过红线。

## 五、AI 员工与提示词

1. **先知道该干什么、怎么干，再动手。**
   - 2026-10-16 原话：“AI 在做一件事之前首先就是要知道自己该干什么！怎么干！”
   - 任务卡负责“该干什么”，技能库负责“怎么干”，执行循环负责“现场应变”。
2. **聊天助手与员工不是同一个角色。**
   - 聊天助手负责理解、讨论、规划、提出任务；
   - 员工角色负责在明确任务卡和技能约束下执行；
   - 两者不能用同一套系统提示词，也不能共享同一套工具权限。
3. **员工只干该干的。**
   - 任务下限：本职步骤一件不少；
   - 任务上限：任务之外的事一件不多；
   - 发布流程里的封面、合集、声明、位置属于本职步骤，不能误判为“不该管”。
4. **技能要沉淀。**
   - 每个环节第一次探索后形成技能 / 页面档案；页面改版后更新档案；
   - 技能不是装饰页面，而是员工执行时可读取的知识。

## 六、前端体验

1. **苹果风、极简、干净、有美感。**
2. **全站一套壳、一套组件、一套样式。**
   - 页面切换不能闪烁、跳动；
   - 侧栏常驻，内容区只换视图；
   - 不允许每页各写一份侧栏、按钮、输入台和弹窗。
3. **信息优先，空间用满。**
   - 功能页不要留大量无意义左右空白；
   - 用户第一眼要看到最重要、最多的信息；
   - 输入框固定在稳定位置，不让用户滚到底部才能输入。
4. **深色 / 浅色主题必须跨壳和内容区一致。**
5. **可访问性和可读性。**
   - 字号、行高、对比度、焦点态、键盘操作要稳定；
   - 消息中的长文本、列表、代码块、链接不能溢出或挤成一团。

## 七、工程与交付

1. **先调研，再设计冻结，再施工。**
   - 没有先例调研、PRD、技术方案、接口契约、E2E 用例骨架，不写功能代码。
2. **先写会失败的验收用例，再实现。**
3. **测试分层，不以 E2E 代替全部测试。**
   - 领域规则用单元测试；
   - IPC / 工具契约用契约测试；
   - 任务生命周期用集成测试；
   - 用户完整动线用 E2E；
   - 对话、任务、空态、深浅色用视觉回归。
4. **交付 = 代码 + 测试 + 打包 + 装机 + 真实内核冒烟 + 证据。**
5. **封版三件套：git tag + CHANGELOG + 存档 zip。**
6. **一次只做一个最小完整工作单元，不允许边做边插队。**
7. **不能把“按钮存在 / 页面能渲染 / 源码里有某段字符串”当成功能可用。**

## 八、明确禁止的做法

- 禁止把某个行业写死进系统提示词、默认任务或页面示例；
- 禁止首页输入默认走任务派发；
- 禁止聊天和任务共用一套提示词、上下文和工具面；
- 禁止纯聊天擅自启动发布浏览器；
- 禁止用固定选择器脚本冒充 AI 现场操作；
- 禁止自动任务和派活各写一套台账；
- 禁止把任务视图塞进聊天消息流里冒充“任务详情”；
- 禁止用 2000 字截断悄悄破坏历史消息；
- 禁止在测试或交付时让窗口抢占用户桌面；
- 禁止在没有验收证据时宣称“完成”。

## 九、需要产品负责人确认的两个交互决策

这两项会直接决定重构后的首页和任务入口，必须先定，后面才好冻结设计。

1. **首页默认行为**
   - 推荐：发送 = 新建一个独立聊天会话；
   - “派活”作为明确动作，由用户点击或由 AI 在聊天中提出任务卡后确认。
2. **任务创建方式**
   - 推荐：AI 在聊天中先把任务拆成任务卡（目标 / 输入 / 产出 / 约束 / 审批点），用户确认后才进入执行；
   - “全自动”只预授权低风险步骤，发布、删除、支付永远人工确认。

> 这两项确认后，才进入《重构总纲》的 Phase 0 设计冻结。
