# J.Co 项目开发经验总结（2026-10-16 定稿版）

> 本文档是 J.Co 项目（自媒体 AI 工作台）从 2026-10-15 启动至 2026-10-16 前端定稿期间的全部开发经验沉淀。
> 覆盖：设计体系、前端工程架构、稳定性与性能、调试方法论、协作流程、可复用资产、教训总表。
> 目标读者：项目负责人（产品负责人）、后续接手的开发者/AI。**任何重大改造前，先读本文档和 README。**

## 一、项目概览

### 1.1 定位与用户

- **产品**：J.Co，自媒体 AI 工作台（Electron 桌面应用）。
- **用户画像**：完全不懂技术的普通人（"手机都可能用不明白"级别的普通小白）。一切交互设计、文案、视觉都必须围绕这个前提。
- **产品路径**：先自用跑量 → 再对外出售；细节改动以"让客户满意"为最终标准。
- **核心工作流**：选题/对标 → 素材 → 创作（文案）→ 做视频 → 后期 → 发布 → 运营。

### 1.2 技术栈（事实基线）

| 层 | 技术 | 要点 |
|---|---|---|
| 壳 | Electron **44.7.0（精确钉版）** | DSH 内核原生插件只认 43 / 44.0 / 44.7 / 45α 的指纹，升级会炸 |
| 前端 | 无构建静态 HTML/CSS/JS | 14 个页面直接 `loadFile` 加载；改原型=改应用 |
| 样式 | 单一来源 `设计原型/assets/jco-ui.css`（J.Co UI Kit，281 个零件） | 见第三章 |
| 内核 | DSH（DeepSeek Harness），`sdk` profile | 子进程托管，含 90 秒超时 + 自动重置 |
| 模型 | Agnes（内置）/ OpenAI 兼容接口；chat / image / video 三类分开配 | 存 `app/kernel/model-config.json`（含 Key，**不入版本库**） |
| 数据 | localStorage JSON 单键（`jco-chats-v1`、`jco-drafts-v1`、`jco-tasks-v1` 等） | 跨页共享、跨重启保留；有清理与防累积机制 |
| 设计标杆 | 本机 Marvis 应用（极简）+ 苹果风 + DSH 前端（交互参照） | Marvis 设计语言已数字化（442 个变量提取） |

### 1.3 时间线（简）

1. 逆向解析 Marvis → 调研自媒体工作流与开源项目 → 方向拍板（桌面端、自用转出售）。
2. 前端从零重做：首页、总管、逐环节页面设计（反复打磨 7+ 轮反馈）。
3. "做不出想要的效果" → 系统学习前端设计 → **Marvis 设计语言全量提取** → 全站对齐。
4. "一点一点改不是办法" → 本质革命：**UI Kit 单一来源 + 视觉守门员**。
5. 稳定性战役：内核超时、画面冻结防范、会话卡顿围剿。
6. 功能补全：自动任务、技能库、会话操作（全站）、剪辑台重做。
7. 布局终战：首句从顶、输入台统一、内容铺满、助手球归位。
8. 前端定稿 + 双重保险（Git + Zip）。

## 二、设计体系经验（最核心的沉淀）

### 2.1 标杆必须"数字化"，不能靠感觉

**做法**：把本机 Marvis 前端的构建产物拆开。事实是——**JS 被混淆不可读，但 CSS 是原样的**（1.1MB 主样式）。从中提取出 **442 个 CSS 变量**与全套实际数值，形成《Marvis设计语言-提取报告》。

**结论：设计不是"感觉"，是"数值字典"。** 有数可依，才能 12 个页面不走样、AI 接手不跑偏。

### 2.2 "赏心悦目"的本质（三件套）

调研了 shadcn/ui、Storybook、Semi Design、Ant Design、Tailwind、Style Dictionary、Chromatic、Radix 等专业工具后的结论：

1. **词汇表极小，而且从不乱用**。Marvis 全站：文字只有 12/13/14/16 四档（大标题例外）、字重只有 400/500/600、圆角只有 8/12/20/28、强调色只有一个蓝。好看的第一来源不是创意，是**约束**。
2. **规矩只写一遍，全产品引用同一份**。DSH 几百个按钮只有一个定义；Marvis 几百个组件背后是同一本字典。这就是"想不一致都难"的工程原因。
3. **防走样靠机器，不靠眼力**。Chromatic 官网原话："即使 AI 写代码，也能强制你的 UI 标准"。我们落地为"视觉守门员"（见 3.3）。

### 2.3 J.Co 最终设计数值（字典摘要，详细见 README 设计标准章节）

| 项目 | 值 |
|---|---|
| 页面底色 / 卡片 / 浅格 / 侧栏底 | `#f7f7f7` / `#ffffff` / `#f0f0f2` / `#f5f5f7` |
| 文字（黑 alpha 阶梯，柔和折中版） | 主 `rgba(0,0,0,.75)` / 次 `.55` / 弱 `.38` |
| 悬停 / 选中 | `rgba(15,15,15,.06)` / `rgba(15,15,15,.10)` |
| 强调色 | `#0080ff`（深色模式 `#0a84ff`） |
| 语义色 | 绿 `#248a3d` / 红 `#d70015` / 琥珀 `#b26800`（各带 tint） |
| 字号 | 12 / 13 / 14 / 16（大标题另算；聊天正文 16 系） |
| 字重 | 400 / 500 / 600 |
| 圆角 | 8 / 12 / 20 / 28（微件 4；保留超椭圆 `corner-shape: superellipse(1.5)`） |
| 阴影三档 | 卡片 `0 4px 10px rgba(0,0,0,.03)`；浮层 `0 8px 16px rgba(0,0,0,.08)` 或发丝+投影 `0 0 1px rgba(0,0,0,.3), 0 4px 14px rgba(0,0,0,.1)`；模态=多层堆叠配方（token `--shadow-modal`） |
| 滚动条 | 4px 极细、灰色滑珠 |
| 内容区 | 铺满主区、左右边距 32px（不设 max-width） |
| 底部输入台 | 浮岛式：与内容同宽、圆角 28、`--shadow`、距底 14、右侧留 74px 给助手球 |
| 侧栏语法 | 分组标签=素面小字（悬停只变色，**不许出现灰块**）；条目=悬停浅灰/选中稍深；**选中一律不加粗**；任何时刻侧栏只有一个灰块 |

### 2.4 视觉经验要点（为什么这么设计）

1. **阴影是"光"，不是"脏"**。旧版弹层阴影 alpha 高达 0.18~0.32，透着"重"和"糊"；换成 Marvis 三档轻配方（3%~10%）后立刻通透。**阴影的重量的感知差远大于其 alpha 值差**——从 0.18 降到 0.08，是"专业感"的最大单点改善。
2. **文字用"黑的不同透明度"而不是多套灰**。灰分两套（系统灰、自定义灰）必然跑偏；单一黑 alpha 阶梯天然和谐。
3. **字号必须收敛，消灭半档**。历史上有 10.5/11.5/12.5/13.5/14.5/15/15.5/16.5/17 九种"半档字"。收敛到 12/13/14/16 后，界面瞬间"安静"。**半档是 AI 味和业余感的强信号。**
4. **交互层级要有梯度**：素面 < hover(.06) < selected(.10) < pressed（更深）。任何两个层级"同深"就会出现"两个灰块打架"的观感（侧栏问题的根因）。
5. **相邻元素几何必须对齐**：圆角、高度、左右缩进。侧栏"分组块 30px/缩进 6px/圆角 8"与"条目块 34px/缩进 0/圆角 12"叠放，是"不协调"的物理根源。统一后（分组素面化）问题消失。
6. **对比度有底线**：正文 ≥4.5:1；弱文字至少 3:1 且只用于辅助信息。柔和 ≠ 看不清。

### 2.5 布局经验

1. **对话流方向**：消息**从顶部开始向下排**（"第一句话在顶上"），打开历史从顶部看；发送新消息自动跟随到最新。**"贴底布局"在消息少时会产生"上空一片"的怪异感**（这是反复确认后的最终结论，参见 6.3 沟通案例）。
2. **底部输入台统一为"浮岛式"**：以前三种形态并存（全宽毛玻璃贴底条 / 920 窄卡 / 悬浮卡），是"歪七扭八"的根源。统一后：与页面内容同宽、同圆角、同阴影、同距底。
3. **悬浮元素的"留位"原则**：浮动助手球与输入台"同排"的可行实现是——**输入台右侧专门留 74px 位**，而不是让球叠上去或飘到上方。**浮动元素要么留位，要么避开，不要叠。**
4. **右上角可折叠面板**（对照 DSH）：默认收起（内容区全宽）、一键滑入、点外面/Esc/Ctrl+Shift+B 关闭、状态记忆。面板高度封顶 2/3 屏。

## 三、前端工程架构经验（第二核心）

### 3.1 病根：12 份拷贝

初期每个页面各写各的样式（每页 20~45KB 内联 CSS）。后果：

- 同一个按钮在 12 个文件里各活各的 → "这边和那边不一样"不可避免；
- 改一个公共样式要写脚本同步 12 处 → "一点一点改"的低效循环。

**数字化诊断**：全站共 21 万+ 字节的重复样式；同一组件最多存在 4 个版本（如主按钮 40/42/46 高度）。

### 3.2 解法：UI Kit（单一来源）

**产出**：`设计原型/assets/jco-ui.css`——全站唯一的一份公共样式（281 个零件）。12 个页面全部改为 `<link>` 引用；页面 `<style>` 只留"本页独有"。**从此：改公共样式=改一处，12 页同时生效。**

**抽取算法（自研工具链，脚本可复用）**：

1. **CSS 块切分**：按大括号配对切顶层规则；必须跳过注释与字符串（`content: "}"` 类陷阱）。
2. **指纹比较**：先逐字节；发现只有约 1/3 完全一致 → 引入"归一化指纹"（去注释、压空白、**保护引号内字符串**）。
3. **实例序号配对**：同一选择器多次出现（如同页两个 `@media dark` 块）按出现序号一一配对，避免错位比较。
4. **投票**：同一"选择器+实例"在 12 页里取多数派版本进共享；少数派留在各自页内（保持各行原行为）。
5. **防泄漏铁律（血的教训）**：**只有 12/12 页完全一致的版本才允许抽取**。早期"多数派抽取"曾导致 `main.main` 这类"只在部分页存在的规则"被抽进共享，让"原本没有该规则的页面"凭空吃到样式——被逐元素验证当场抓住。**共享文件会被所有页面加载，任何"部分页规则"进入共享即等于全局泄漏。**

**变更流程（固化，每次改公共样式都必须走）**：

```
① 快照 baseline（写入 work 目录，供验证对比）
② restore：把现有共享块“还原”进 12 页（否则重抽会丢失旧共享——生成式覆盖陷阱）
③ 统一脚本修改（逐页精确替换 + 报告命中数；未命中即预警）
④ 重抽（重新生成 jco-ui.css）
⑤ verify：逐元素 computed style 对比（见 3.3），要求零差异或“计划内差异清单”
⑥ QA 回归 + 截图抽查
⑦ 重启应用 + 存档（zip）+ git 提交
```

**完整性校验**：每个页面所有 `var(--x)` 引用必须有定义（曾抓出：首页缺 `--picked`、管家团队页缺 `--green-tint` 两个"引用未定义"的既存 bug）。

### 3.3 视觉守门员（自动验证体系）

**工具**：`verify-computed.cjs`——对每页"改动前 vs 改动后"**全量逐元素**对比：

- 采集范围：**2834 个元素 × 36~40 项 computed 属性 + 几何 rect**；
- 关键工程细节：
  - 等待 `link.sheet` 就绪再采集（否则新结构下样式没加载完，"全无样式"是测量假象）；
  - **采集时排除 `<link>` 元素**（新结构多一个 link 会让逐索引对比整体错位——曾把 2834 元素的对比搞成满屏假差异）；
  - 注入动画冻结样式、先清 localStorage 动态状态，消除测量噪音。
- 验收标准：**零差异**，或者**"计划内差异清单"逐条可解释**（如"侧栏圆角 28→20 共 2 项""图标修复引起的 16 项"）。

**这套体系的关键战果（每个都是真 bug 或真修复）**：

| 时间 | 事件 | 结果 |
|---|---|---|
| UI Kit 二轮重抽 | `--font` 缺一个分号，导致 `--bg` 定义被吞、全站字体/背景失效 | verify"全页无样式"当场抓住，60 秒定位 |
| 严格抽取前 | `main.main` 规则泄漏到首页 | verify 抓出 3 项差异 → 确立 12/12 铁律 |
| 图标全集补全 | 12 页里此前"宽度为 0、根本显示不出来"的图标恢复 | verify 呈现为稳定的 16 项几何差异=**修复效果可视化** |
| 每轮统一 | 任何"意外差异"都逃不过 2834 元素的对比 | 0 意外差异成为交付标准 |

**另一道门**：`preflight`（规则检查：破折号、`transition: all`、`scale(0)` 入场、focus-visible 缺失、纯黑白等）——12 页全绿。

### 3.4 其他架构决策

1. **超椭圆保留**：`corner-shape: superellipse(1.5)` 是全站统一开关，圆角观感"苹果味"的来源；但对正圆/胶囊元素强制 `round`（组合选择器清单），避免变形。
2. **图标字体是子集**：`tabler-icons.woff2` 只含收录的字形。**新增图标前必须验证字形存在**（曾发现 `ti-player-play` 内容为空——直接踩坑）。图标全集 80 个，收录原则：先验证、再使用。
3. **设计系统页**（`J.Co设计系统.html`）：零件橱窗，色彩/文字/圆角/阴影/侧栏零件/菜单/按钮/图标全套陈列；新页面从这里"取件"，不许自创。
4. **页面私有 vs 公共的判断**：功能页的领域组件（如做视频页的技能格）保留页内；任何"跨页出现的通用件"一律收编进 UI Kit。

## 四、稳定性与性能经验

### 4.1 内核调用：必须有"最终期限"

**事故机制**：内核（DSH 子进程）一旦挂起，`ask()` 的 Promise 永不 settle → IPC 永不返回 → 聊天永远"转圈"、所有对话/生成操作无响应 → **用户体感"整个前端死了"**。

**修复**（双层防线）：

1. 主进程侧：**90 秒总超时**（`Promise.race`），超时后**重置内核**（关闭子进程、下次自动重建）并返回可理解的错误文案；**重置动作本身再加 3 秒硬超时**（否则重置挂住会把请求又一次永久拖住）。
2. 渲染端：100 秒兜底超时。

**通则：任何依赖外部进程（子进程/网络/模型）的调用，必须有"最终期限"+"可理解的失败文案"+"自动恢复路径"。** 用户可以不成功，但不能"没有反应"。

### 4.2 画面冻结：识别合成器风险

**机理**：Windows + Electron 下，大面积高强度 `backdrop-filter`（如 `saturate(180%) blur(25px)` 的侧栏玻璃、弹层的 blur）在部分机器/GPU 上会触发**合成器冻结**——JS 主线程还活着，但画面不动、点击无响应，**只能重启**。

**处置**：

- 侧栏玻璃降级：`saturate(180%) blur(25px)` → `blur(10px)` + 底色更实（0.78→0.92）（观感几乎不变，风险大降）；
- 弹层 blur(4px) 全部移除；
- 保留"轻模糊"的视觉语言，但**拒绝"高饱和 + 大半径"的组合**。

**通则：视觉效果的"渲染成本"要单独评估**；在桌面端（尤其 Windows），大面积模糊是稳定性风险项，不是免费的美化。

### 4.3 渲染性能：列表三大原则

**场景**：切换长历史会话（120+ 条消息）曾存在卡顿风险。

**修复**：

1. **批量插入**（DocumentFragment 一次性挂载，替代逐条 append）；
2. **历史无动画**（只有"新产生的内容"才有入场动画；重放历史全部直接呈现）；
3. **渲染有上限**（最多渲染最近 80 条，更早的显示"已省略"一行；数据层每会话硬上限 120 条）。

另加"切换动作延迟到首帧后 60ms 执行"，避免"页面加载 + 会话渲染"挤在同一帧。

**实测**：120 条长会话渲染 **57ms**；跨页点会话到总管就绪 **84ms**；连续切换 20 次每次约 **40ms**。

### 4.4 数据层：新建操作的幂等与清理

**事故**：会话列表堆积 7 个"新会话"（每次点"新会话"都新建一个空会话，且从不清理）。

**修复三道锁**：① 打开时自动清理"非活动的空会话"；② "新建"自动复用已有的空会话；③ 删光后自动补一个空会话兜底（列表永远可用）。

**通则：任何"新建"入口都要防狂点（幂等/复用）；任何"可增长的列表"都要有上限与清理。**

### 4.5 事件交互：两个经典的指针陷阱（剪辑台实战）

1. **`setPointerCapture` 不要在 pointerdown 时就抢**。按下即捕获会导致后续所有点击的落点被重定向到捕获元素（实测：`pointerdown target=clip`，`click target= tl-body`）→ 元素点不中。**正确做法：判定"真正进入拖动"（位移 > 4px）后才捕获。**
2. **"拖动结束吞掉点击"的抑制标记，必须在下次 pointerdown 时重置**。否则上一次拖动的标记会误吞下一次点击。
3. **拖拽与点击的区分**：位移阈值 4px；阈值内抬起=点击（原行为），超过=拖动（执行拖动逻辑并抑制随之而来的 click）。

## 五、调试方法论（案例复盘）

### 5.1 "卡死"类问题的分层排查法

"卡"在用户语言里是四种完全不同的东西，**先分类，再工具**：

| 类型 | 特征 | 检测手段 |
|---|---|---|
| 主线程卡死（JS 死循环） | evaluate 超时 | 探针：`evaluate(new Promise(setTimeout))` 是否超时；进程 CPU 是否 100% |
| 渲染/合成器冻结 | JS 活着、画面不动 | 截图是否卡住；问题与"大面积 blur/动画"的相关性 |
| 遮罩遮挡 | 看得见画面、点不动 | elementFromPoint 打点；全屏 fixed 层扫描 |
| 等待无反馈（假死感） | 功能"没反应"但界面可点 | 检查是否有"永不返回"的异步/超时缺失 |

**排查武器库（全部实际用过）**：

- 三环境复刻：浏览器逐页扫描 → Electron 真机链式跳转（模拟"挨个检查"）→ 关键动线复刻（首页发送→总管开干）；
- **事件打点**：在 document 上挂 capture 级 `pointerdown/click` 记录 target（一案定音：发现 click 落点被重定向）；
- 压力数据（10 倍于真实数据造会话）快速暴露性能悬崖；
- 进程侧取证：窗口 `Responding` 状态、CPU 累计、userData 数据体积（32KB 数据直接排除"数据爆炸"假设）。

### 5.2 批量脚本的安全要点（AI 写脚本必守）

1. **先快照**（baseline 目录），失败可秒回；
2. **每次替换都报告命中数**；预期 N 处，命中 ≠ N 立即预警（本次开发中凭此抓出过多次"未命中/误伤"）；
3. 用**足够长的上下文锚点**，避免"同文本多处出现"的误替换；
4. 改完**先验证再声明成功**（computed 对比 / QA / 截图三选一，重要改动三者都要）。

### 5.3 环境与编码坑（Windows 实录）

| 坑 | 症状 | 解法 |
|---|---|---|
| PowerShell 5.1 读 UTF-8 无 BOM 脚本 | 中文路径变乱码（"备份"→"澶囦唤"），脚本报"路径不存在" | 脚本文件保存为 **UTF-8 with BOM**，或让 pwsh 执行 |
| `rg` 不支持 look-around | 正则报错 | 换 `--pcre2` 或用 node 脚本解析 |
| file:// + 中文文件名 | playwright 打不开 | `encodeURIComponent` 文件名；静态资源用相对路径 |
| Electron 的 prompt() | 不可用 | 重命名等交互一律自建（内联输入框） |
| 剪贴板 API 权限 | 可能被拒 | 失败兜底文案；保持"复制→提示成功/失败"的诚实反馈 |

### 5.4 验证驱动开发的威力（铁律）

本项目的多个"真 bug"全部由自动化验证先于用户发现：分号 bug、规则泄漏、图标 0 宽度、索引错位……**AI 批量改代码时，人眼不可信，只有机器对比可信。**

## 六、协作与流程经验（与产品负责人）

### 6.1 沟通原则

1. **一切交付要"可点的实物"**：截图、对比图、能打开的文件；不用"我优化了架构"这类抽象说法（要翻译成"改一处、全站生效"）。
2. **决策主权归用户**：AI 只做两件事——拍板前给足候选（含默认推荐），拍板后执行到底。这条既是产品原则（页面里也这么设计），也是协作原则。
3. **反馈必须"具体化"**：用户说"不协调"，要翻译成可执行的物理描述（"两个错位灰块叠加 + 加粗"）；用户说"太深了"，翻译成具体数值（对比度、alpha）。
4. **给用户两个抓手**：①截图/画图（问他"画一下"效果最好）；②"一句话验收标准"（他能用眼睛确认的东西）。

### 6.2 需求理解的著名教训："从下往上"案

- 用户反馈"对话从上往下！哪个 APP 是从下往上的？"——首轮**理解反**（做成了"贴底"）；
- 用户画图指出"第一句话应该从顶上开始"——一张手绘图解决全部歧义。
- **教训**：① 方向类描述（上/下、大/小、深/浅）极易误解，**必须让用户画图或指认**；② 有歧义时先做"最保守的小改动"问一句，再全量执行；③ 修正方向时要同步修正所有历史连带（如"贴底"时期做的滚动行为）。

### 6.3 存档与回滚体系（三层保险）

1. **每轮 zip 存档**：`备份\存档-<轮次>-日期.zip`（app 源码 + 全部页面 + 文档）；每轮改动前先打"改前档"，完成后打"改后档"；
2. **工程快照**：`work\backup-html-*`（逐轮逐阶段的页面快照，验证的 baseline）；
3. **Git 版本库（2026-10-16 起）**：
   - `J.Co` 目录已 `git init`；"前端定稿"标签：`前端定稿-2026-10-16`；
   - **规矩：每次前端改动前后各留一个"版本点"**，提交信息用中文写明做了什么；
   - `.gitignore` 排除：`app/node_modules/`、`备份/`、`*.zip`、**`app/kernel/model-config.json`（含 API Key，绝不入库）**；
   - 回滚方式：整体 `git checkout <版本/tag>`；单文件 `git checkout <版本> -- <文件>`。
4. **回滚说明文档化**：`备份\回滚说明-*.md`——小白能照抄、AI 能执行。

### 6.4 文档沉淀的四个作用

- 调研报告（AI 自媒体工作流 / 专业工具链）：**防失忆**（为什么做这个决定）；
- 设计字典（Marvis 提取报告 + README 设计标准）：**防走样**（AI 换人也不跑偏）；
- 结构规则（UI Kit 流程 + 守门员）：**防破坏**（改之前知道要过哪几道门）；
- 存档/回滚说明：**防背锅**（任何一步都能退回去）。

## 八、教训总表（现象 → 根因 → 对策 → 预防）

| # | 现象 | 根因 | 对策与预防 |
|---|---|---|---|
| 1 | 12 个页面"各长各的"，改一处要改 12 处 | 12 份样式拷贝 | UI Kit 单一来源；"通用件必收编"制度 |
| 2 | "部分页规则"泄漏全站（main.main） | 共享文件被所有页加载 | **只有 12/12 一致的规则才可抽取**（铁律） |

| 4 | 侧栏"两个灰块打架" | 分组 hover(.10) 与选中(.10) 同深 + 几何不一致 | 交互灰度梯度（.06/.10）；相邻元素几何对齐 |

| 6 | 聊天"永远转圈、像死了" | 内核调用无超时 | 90 秒超时 + 自动重置 + 3 秒重置超时 |
| 7 | "点哪都没反应、必须重启" | （排查后）大面积高强度 blur 的合成器冻结风险 | 玻璃效果降级（blur 10 + 底色更实）；弹层 blur 移除 |
| 8 | 切换长会话卡顿风险 | 逐条插 DOM + 全体重放动画 | 批量插入 + 历史无动画 + 80 条上限 |
| 9 | 会话列表堆积 7 个"新会话" | 新建不幂等、无清理 | 清理 + 复用 + 兜底三件套 |
| 10 | 剪辑台"点不中片段 / 吞点击" | pointerdown 即捕获指针；抑制标记不重置 | 进入拖动才捕获；pointerdown 重置抑制标记 |
| 11 | 输入台三种形态"歪七扭八" | 各页独立演化 | 统一为浮岛式（同宽/同圆角/同阴影/同距底） |
| 12 | 助手球"飘"与"叠" | 锚定策略错误（放上方/无留位） | 与输入台同排 + 右侧 74px 专属留位 |

| 14 | 脚本批量替换"未命中/误伤" | 锚点过短/同文本多现 | 长上下文锚点 + 命中数报告 + 快照回退 |
| 15 | Windows 脚本中文乱码 | PS 5.1 读 UTF-8 无 BOM | 脚本加 BOM；路径编码纪律 |
| 16 | 重启后旧会话续聊报 `already exists`（用户见英文红框） | SDK rc 版服务端只"新建"不"恢复"；持久化层同 id 冲突（M5 预演时揪出，见《缺陷记录-2026-10-16-会话续聊》） | bridge 层"会话别名自动恢复"（冲突→换本进程 id 重试并记忆）；E2E 回归固化；跟进内核 resume 能力 |

## 九、面向下一阶段的建议

1. **前端继续沿用现有体系**：新增页面从 UI Kit 取件 → 过 preflight + 守门员 → git 提交；不要绕过流程。
2. **功能先做"真"**：所有演示态（发布预演、账号演示、任务调度）在进入"客户版"前逐项真化；本条已在 README 待办中登记。
3. **若升级为"客户版"技术栈**（React + shadcn/Semi + Storybook + Chromatic）：现有设计字典、数值、验证思路可 100% 继承；UI Kit 的设计 token 可直接迁为 Tailwind/Semi 的 theme。
4. **打包交付时**：Electron 44.7.0 精确版本；内核运行时随包内置（用户无需安装 DSH）；自带首次启动引导。
5. **数据与隐私**：模型 Key 只在本地配置、不入版本库；登录态"只在本机、不上云、不搬家"（矩阵账号原则）。
