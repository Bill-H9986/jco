> 调研日期：2026-10-17
> 调研目的：判断“给 AI 建立持久化项目认知索引”是否适合 J.Co，以及 J.Co 现有 AI 软件开发工作流缺了什么。

## 二、这个项目是什么

### 2.1 一句话

**AOCI-CODE 是位于 AI Agent 和代码库之间的“认知基础设施”：它把代码、配置、测试和数据库结构整理成一份持久化、可版本化、可治理的纯文本索引，让 Agent 在行动前先获得整个系统的语义地图，而不是每个任务都重新搜索代码。**

它不是一个新模型，也不是 RAG / CodeGraph / LSP 的替代品。

### 2.2 项目事实

核对时间：2026-10-17。

| 项 | 事实 |
|---|---|
| 仓库 | `aoci-spec/aoci-code` |
| 当前版本 | `v0.1.0-rc21`（2026-10-14 发布） |
| 语言 | Go |
| Stars / Forks | 约 1,586 / 201（核对时） |
| 许可 | FSL-1.1-MIT（Fair Source / source-available；不是传统 OSI 开源） |
| 运行形态 | 单个 Go 二进制；CLI + stdio MCP Server |
| 数据边界 | 本地优先；只读源码 / 数据库结构；不联网、不上传、不保存数据库凭据 |
| 规模声明 | 支持 50 万行以上系统；README 称实测 70 万行商业系统，索引约 300K token |
| 首次索引成本 | README 称 20 万行约 1 小时（取决于模型和 Agent 速度） |

### 2.3 许可提醒

这不是可以随意拿来做竞品的“无限制开源”：

- 允许内部使用、非商业教育、非商业研究，以及与持证方相关的专业服务；
- 不允许将软件做成与其功能实质相同的商业产品或服务；
- 发布两年后自动转为 MIT。

如果只是把 AOCI 作为 J.Co 开发期的内部工具，风险较低；如果要把它打包进对外销售的 J.Co，必须先做许可证评估。

### 2.4 本机安全试点结果（2026-10-17 13:43）

为避免影响正式工程，本轮只在 `work/aoci-pilot/repo` 的 J.Co 源码副本上做了初始化 / 扫描 / 诊断，没有修改正式工程、没有安装到 J.Co 用户端。

执行结果：

- 下载的 `aoci_0.1.0-rc21_windows_amd64.zip` SHA-256 与官方 `SHA256SUMS` 一致；
- `aoci --version`：`0.1.0-rc21`；
- `aoci init`：识别 147 个 Git 跟踪文件；116 个 `index` 文件、31 个 `observe` 文件；估算 Whole-Index 约 **14,560 tokens**；
- `aoci scan`：151 个文件，1.7 秒完成；114 个文件需要写条目；3 个二进制文件跳过；按每轮最多 50 条，约 **5 轮 Maintain**；
- `aoci capabilities`：`volumes-v1`，MCP 工具 9 个；
- `aoci doctor`：全部检查通过；Codex MCP 已写入项目级 `.codex/config.toml`；AI 增强层默认关闭，未把源码发到任何外部端点。

试点也暴露了接入摩擦：

- `init` 会往 `AGENTS.md` 追加一大段 AOCI 规则区块（本次约 107 行），并生成 `AGENTS.md.backup.*`；J.Co 要求 `AGENTS.md` 与 `CLAUDE.md` 完全一致，正式接入必须先把这段规则合并进两边，不能直接覆盖。
- 会新增 `.aoci/`、`aoci.txt`、`aoci.meta.txt`、`aoci.code.txt`、`.gitattributes`，并修改 `.gitignore`；这些都要走变更单和 review。
- Codex 只会对“受信任项目”加载项目级 `.codex/config.toml`，首次使用需要信任本仓。

结论：J.Co 这个规模（约 2.4 万行、105 个自写文件）非常适合试点；索引体量不大，真正成本在首次 5 轮语义创作和后续维护纪律，而不是扫描性能。

## 三、它的核心方法

### 3.1 索引不是一次性摘要

AOCI 把正式认知写成纯文本资产，随项目进入 Git：

- `aoci.txt`：Root，声明当前认知集合和 Volume；
- `aoci.meta.txt`：Meta，标签字典、FRAS 规则、预算和创作约束；
- `aoci.code.txt`：代码对象的语义条目；
- `aoci.database.txt`：可选的数据库表级认知。

索引可以 diff、审查、版本化和回滚；不是藏在某个会话里的摘要。

### 3.2 FRAS：一条记录记什么

每个受管对象（文件或表）有一条紧凑条目：

- **F — Function**：它负责什么；
- **R — Relations**：安全理解或修改它时还必须关注什么；
- **A — API**：它对外提供哪些接口、命令、格式或可观察契约；
- **S — Non-obvious constraints**：F/R/A 之外、但对正确修改很关键的约束、例外和边界。

例如：

```text
atomic.go[CG9L]: F:提供持久化替换 CAS、创建 CAS、原子写入和禁止覆盖的恢复移动 | R:code:internal/fs/atomic_exchange_linux.go,code:internal/fs/atomic_exchange_windows.go,code:internal/fs/lock.go | A:AtomicWrite,AtomicWriteCAS,AtomicCreateCAS,AtomicMoveCAS | S:原生发布绝不会降级为覆盖式重命名；遇到竞态、不安全类型或无法验证的字节时，必须保留第三方状态并失败关闭
```

这比“文件路径 + 一句话摘要”多了两层关键信息：**强关系**和**不能改坏的约束**。

### 3.3 治理流程

典型流程：

```text
init → scan（建立 Baseline）
  → Agent 阅读源码 / 证据并创作索引
  → verify / check / guide 收敛到 aligned
  → 正常开发任务
  → 代码和测试稳定后，MCP 引导 Agent 增量维护受影响条目
  → 重新 aligned
```

它不只保存“写了什么”，还保存：

- Managed Scope：哪些对象进入正式认知；
- Drift：Missing / Orphan / Stale / Unbaselined / 换行变化等；
- 源码 SHA-256 绑定；
- Plan / Review / CAS / 原子写入 / Baseline / Recovery；
- Ledger 和可审计的回执。

### 3.4 9 个 MCP 工具

README 当前列出的固定工具面：

| 类别 | 工具 |
|---|---|
| 认知读取 | `aoci_rules`、`aoci_overview`、`aoci_get_entries`、`aoci_search` |
| 认知维护 | `aoci_maintain`、`aoci_update_entry`、`aoci_remove_entry` |
| 辅助证据 | `aoci_header`、`aoci_report` |

### 3.5 长会话与上下文压缩

这是它和“普通 AGENTS.md + README”最本质的区别。

AOCI 的 `cognition-refresh.md` 明确规定：

- 正常任务开始时读取一次完整的 Whole-Index；
- 当发生 **Host context compaction** 时，不能把摘要过的索引当成可靠认知；
- 必须重新读取规则，声明 `context_compaction`，然后拉取完整 Overview；
- 按 `next_cursor` 一段段拉完，确认交付，再重新 Attestation；
- 语义漂移达到阈值（默认 30 个不同路径）或跨阶段时，提示维护；
- 未对齐时，源码和测试仍是实现事实，不能拿旧索引冒充最新状态。

这正好回答了你担心的“会话一长、上下文压缩后跑偏”的问题。

## 四、它和 J.Co 现有工作流的关系

### 4.1 J.Co 已经有的

J.Co 的《软件开发工作流标准》并不空：

- §5.2 开工仪式：读 `AGENTS.md` → `README.md` → 工作流标准 → 当前里程碑设计包；
- §5.1 单一来源纪律；
- §5.4 变更留痕、ADR、复盘；
- 立项 / 设计冻结 / 先红后绿 / 门禁 / 封版三件套 / 对抗审查；
- `docs/plans` 里程碑包和台账；
- Git、测试、审计脚本。

这些是**流程记忆**和**变更记忆**，已经比多数个人项目扎实。

### 4.2 J.Co 缺的

| 缺口 | 现有状态 | AOCI 提供的 |
|---|---|---|
| 全量语义索引 | README 是叙事，台账是里程碑记录，没有“每个文件/模块一行”的全局语义地图 | Whole-Index + FRAS |
| 源码绑定 | 文档可能落后于代码（这次核对已经发现） | 每条认知绑定源码 SHA-256 / Baseline |
| 漂移检测 | 靠人读 README / 跑测试，测试不覆盖“文档是否还真实” | Missing / Orphan / Stale 等漂移分类 |
| 上下文压缩恢复 | 没有正式的重载协议 | compaction 后强制完整 Overview + Attestation |
| 强关系与约束 | AGENTS 只有项目级规则，没有对象级“改它必须看什么” | R 字段 + S 字段 |
| 数据库/数据契约认知 | 本地数据层是 localStorage / JSON，缺少统一语义索引 | Database Volume（可选） |

所以答案是：**J.Co 工作流讲了“开工读文档、单一来源、变更留痕”，但没有讲“机器可读的项目认知索引”和“上下文压缩后的认知重载协议”。AOCI 补的正是这一层。**

## 五、建议怎么用（分三档）

### 档 A：先做零依赖的“轻量认知基线”（推荐先做）

不引入 AOCI，先把 J.Co 自己的认知入口收口：

1. 保留本目录的《项目现状与风险清单》作为“当前事实快照”；
2. 新增一份 `docs/项目认知索引.md`：每个核心模块 / 页面 / 工具一行，写清职责、关系、公开入口、不能改坏的约束；
3. 新增一份 `docs/会话交接协议.md`：上下文压缩后必须重读哪些文件、如何核对 HEAD/版本/门禁；
4. 每次封版或重大变更，更新索引并把它和代码一起提交。

优点：零新依赖、零许可证风险、马上可用。
缺点：仍靠人/Agent 自觉维护，没有源码绑定和自动漂移检测。

### 档 B：AOCI 试点（推荐在分支 / 工作区做）

在不动生产目录的前提下：

1. 从官方 Release 下载并校验 `aoci` 二进制；
2. 在 J.Co 的副本或新 worktree 中运行：

   ```text
   aoci --repo . init --locale zh-CN --agent codex
   aoci --repo . scan
   ```

3. 重启 Codex，让 MCP 生效；
4. 让 Agent 建立 Whole-Index，运行 `verify` / `check` / `guide` 到 aligned；
5. 做一次小改动，观察它是否能正确维护受影响条目；
6. 对比“新会话只读索引”和“新会话读 README + docs”的差异。

本轮安全试点给出的实际参考是：**Whole-Index 约 14,560 tokens、114 个待写文件、约 5 轮 Maintain**。这比“十几分钟”的粗略估算更具体，但仍取决于模型速度和每轮实际完成的条目数。

**注意**：AOCI `init` 会写 `AGENTS.md` 规则区块。J.Co 现在要求 `AGENTS.md` 与 `CLAUDE.md` 完全一致，接入前必须先把生成内容合并进两边，不能直接覆盖。

### 档 C：正式接入（暂不建议）

只有在试点证明以下四点后才考虑：

1. 索引能显著减少新会话的阅读和试错；
2. 索引与代码漂移能被稳定发现；
3. 许可证、二进制分发、升级回滚都能接受；
4. 不会和 J.Co 现有 AGENTS / 台账 / 单一来源纪律产生第二事实源。

## 六、试点验收标准

建议用 1–2 天做一个小试点，按下面标准判断“抄不抄”：

| 标准 | 通过条件 |
|---|---|
| 认知覆盖 | 新会话只看索引 + 证据，能说清主进程 / 内核 / 发布 / 后期 / 数据层的关系 |
| 风险识别 | 能指出本次审计发现的至少 3 个真实风险，而不是复述 README |
| 漂移检测 | 改一个文件后，AOCI 能指出受影响条目并要求维护 |
| 压缩恢复 | 模拟上下文压缩后，能按协议重新加载完整认知，不沿用摘要 |
| 维护成本 | 一次小改动的索引维护不超过改动本身的合理比例 |
| 许可/分发 | 内部开发可用；若涉及对外销售，法律边界明确 |

## 七、不抄什么

- **不把 AOCI 当成“语义正确性证明”**：它明确说绿色只证明结构与治理条件成立，语义仍要源码、测试和人工审查。
- **不让索引取代测试和门禁**：J.Co 的 typecheck / unit / E2E / audit 仍是最终验收。
- **不把 AOCI 直接打进 J.Co 用户端**：它是 RC，且许可证对“竞争性商业产品”有限制。
- **不制造第二套事实源**：J.Co 的代码 / 测试 / 现状快照仍是权威；AOCI 只做代码认知层。
- **不在每个聊天回合都灌入完整索引**：长索引会消耗上下文；按任务开始、阶段切换、上下文压缩时加载。
