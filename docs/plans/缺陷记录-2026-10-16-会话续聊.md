# 缺陷记录：会话续聊跨重启（2026-10-16）

> 按《工作流标准》v1.2「缺陷处理：评估 → 修复 → 验证」三分离执行｜发现于 M5 真机预演

## 一、评估

- **现象**：应用重启后，在**旧会话**（上次运行创建过的）里再发消息，AI 直接回一坨英文报错：
  `session "jco-chat-xxx" already exists`（用户看到"本轮没答上来"红框）。
- **复现**：实例 1 用会话 id 跑一轮 → 关应用；实例 2（新启动）用**同一** id 再跑 → 必现。
- **根因**（两层，均已定位到源码行）：
  1. SDK 服务端 `dsh-sdk-jsonrpc-server` 的 `getOrCreateSession()` **只查内存**：内存没有就 `createSession()`，
     **没有"从磁盘恢复已有会话"的路径**（该 rc 版 SDK 未暴露内核已有的 `agents.resume` 能力）；
  2. 持久化后端 `dsh-session-persistence-jsonl` 的 create 检查 `findLog()`——磁盘已有同 id 日志则抛
     `SessionAlreadyExistsError`。
  3. 合起来：**内核进程重启后，磁盘上存在的会话 id 一律不可再入**。
- **影响面**：重启后点旧会话续聊 = 用户的**日常路径**（发布/运营任务卡续跑、普通聊天续聊都走它）；
  同一次运行内的多轮不受影响（内存命中）。**定性：致命缺陷，立即修复（不排队）**。
- **旁证**：内核会话按**进程工作目录分桶**存于 `~/.dsh/sessions/<cwd 转义>/<会话id>`——产品模式
  （从 app 目录启动）与测试模式各自分桶，互不干扰。

## 二、修复

**位置**：`app/kernel/bridge.mjs`（不动 node_modules 依赖，不改内核协议）

1. **会话别名自动恢复**：
   - 维持一张进程内映射 `sessionAliases: 原会话 id → 实际内核会话 id`；
   - `ask()` 正常用原 id 跑；**仅当**内核报 `already exists` 时，换 `原id + '-r' + 时间戳` 重试一次并记住映射；
   - 之后同一进程内该会话的消息都用映射后的 id（**这次运行内上下文连续**）；
   - 未发生冲突的场景（绝大多数）：**零行为变化**。
2. **测试基建**：`--jco-test` 模式一律走官方兜底路由（`resolveRoute()` 短路）——回归测试稳定、
   不烧 Agnes 配额；只影响开发者测试。

**明确不做（划界）**：不读内核会话存储文件做"历史搬运"（依赖内部实现，脆）；
恢复的内核会话不带旧上下文（见 §四）。

## 三、验证

| # | 验证 | 结果 |
|---|---|---|
| 1 | 行为实验（`work/qa-m5-session.cjs`）：实例1 新 id → 实例2 同 id | 修复前：❌ `already exists`；**修复后：✅ `ok`** |
| 2 | 同进程内同 id 多轮 | ✅ 两轮均正常（"收到"→"好的"） |
| 3 | 回归测试固化 | `app/tests/e2e/session-recover.spec.mjs`：两个应用实例接力、断言不报错——**已进 gate**（8.6s 通过） |
| 4 | 全量门禁 | tsc / biome / vitest / 全部 E2E 通过（随修复提交） |

## 四、遗留（如实记录）

- 恢复的是**新内核会话**：重启后旧会话的第一条消息，AI **看不到该会话更早的聊天历史**（失忆），
  但**功能可用、不再报错**；这条消息之后的上下文正常延续。
- **跟进项**：等内核 SDK 暴露 `resume`（或内核升级）后，改为"真恢复"（带回历史）；
  届时本记录更新为"彻底修复"。
