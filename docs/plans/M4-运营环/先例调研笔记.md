## 一、需求基线（重要：不用凭空设计）

**运营页 UI 已定稿**（`设计原型\J.Co工作台-运营.html`），它本身就是需求定义：

| 定稿元素 | 含义（需求） |
|---|---|
| 今日战报（播放量/新增粉丝/评论，近 7 天） | 数据每天早上自动更新——**真实数据接入** |
| 数据解读样例（"昨晚那条播放是平常的 8 倍……AI 拆出的原因"） | AI 不只报数，还要**拆原因** |
| **评论要你过目**（"8 条等你回，先挑了 3 条重要的 · **AI 拟好稿，你点头才发**"） | 评论回复的完整红线已经写在界面上 |
| 私域线索（"从评论和私信找过来 9 个人，先跟进这 3 个"） | 意向线索的识别与登记 |
| 右下角助手（"这条视频数据怎么样？"） | 数据问答入口 |

## 二、业界先例

### 1. 采集侧：MediaCrawler（NanmiCoder/MediaCrawler，⭐6.7 万）

- 覆盖：小红书/抖音/快手/B站/微博/贴吧/知乎的**笔记与评论爬虫**；
- 性质：独立 Python 爬虫（需登录 cookie、对抗平台协议面）——**重**；
- 我们的取舍：**不做爬虫集成**。运营环的数据源用**已有机制**——"AI + 本机会话服务"打开自己账号的创作者中心页面读取（登录态现成、行为等于普通用户看自己的数据、无额外维护面）。
- MediaCrawler 的**评论字段结构**可作为我们数据层设计的参考（内容/作者/时间/点赞）；将来"对标账号爆款拆解"（选题环）再评估引入。

### 2. 审批流：OpenOPC（见项目《OpenOPC-借鉴笔记》）

- "低风险自动放行、高风险等拍板、**会话级授权**"——评论回复=高风险 → **人点头才发**（与运营页定稿文案一致）；将来可抄"会话级授权"（"这半小时内同类不用再问"）。

### 3. 组织记忆：OpenOPC Self-Grown

- 每次任务后写回记忆条目（做了什么/结果/教训）——与"战报/复盘"呼应；我们的"活动日志"是雏形，运营环可直接受益。

### 4. 评论回复自动化：未发现可照抄的成熟开源

- GitHub 检索无对口高质量项目；结论：**复用我们的发布机制**（会话服务 + 白名单工具 + 任务卡 + 人机检查点）自建，与"发布"同构。

## 三、结论

运营环三块**全部复用发布链路的机制**（AI 操作浏览器 + 任务卡 + 检查点 + 技能注入），
不引入重型框架；差异只在"目标不同"（读数据 / 回复 / 识别线索）与"业务红线"（评论须人点头）。
