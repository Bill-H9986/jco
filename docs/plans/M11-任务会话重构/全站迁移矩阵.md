# M11 全站迁移矩阵

- 日期：2026-10-17
- 目的：保证不是只修首页/聊天/任务，而是整个项目逐步迁移到同一套数据、提示词、组件和任务模型，避免新旧混用。
- 依据：产品负责人多次明确要求“整个项目”“全站”“所有页面”“全部统一”“新旧前端必须统一”。

## 一、原则

1. **全站是一个系统**：不允许新聊天 + 旧设置 + 旧发布长期并存。
2. **一次设计，分批施工**：架构一次定死，页面按波次迁移；不是所有页面同一天改完，但每个页面都必须进矩阵、有负责人、有验收。
3. **单一数据源**：业务数据逐步迁到主进程 store；旧 localStorage 只做迁移期只读兼容。
4. **单一组件源**：侧栏、消息、任务卡、状态徽标、输入台、弹窗、按钮只保留一套。
5. **单一任务源**：页面派活、聊天任务卡、自动任务都走 TaskService。
6. **单一提示词源**：BasePrompt + BrandProfile + RolePrompt + TaskCard + Skills，不在页面里写行业身份。
7. **没有页面可以“暂不迁移”**：只能排在后面的波次，不能永远留在旧架构。

## 三、旧数据 key 迁移表

| 旧 key / 文件 | 新归属 | 迁移策略 |
|---|---|---|
| `jco-chats-v1` / `jco-chat-v1` | conversations / messages | 一次性迁移；旧 key 只读保留一版 |
| `jco-log-v1` | activity / task_events | 迁移为活动记录；不混入聊天 |
| `jco-drafts-v1` | artifacts(draft) | 迁移草稿；保留原文件引用 |
| `jco-materials-v1` | artifacts(material) / materials | 迁移素材索引 |
| `jco-script-v1` | artifacts(script) | 迁移稿件 |
| `jco-inspo-v1` / `jco-radar-v1` / `jco-favs-v1` | topics | 迁移选题数据 |
| `jco-publish-v1` | publish records / artifacts | 迁移发布记录 |
| `jco-login-v1` | accounts / login registry | 迁移登录登记，不迁移真实凭据 |
| `jco-tasks-v1` | automations | 迁移计划模板 |
| `kernel/auto-tasks.json` / `auto-runs.json` | automations / task_runs | 迁移计划与历史；不再作为运行台账 |
| `kernel/task-sessions/*.json` | tasks / task_runs / task_events | 迁移旧任务；状态归一 |
| `kernel/skills.json` / `jco-skills-v1` | skills | 以界面/ store 为唯一源 |
| `jco-mode-v1` / `jco-side-pinned` / 主题等 | settings | 迁 settings store；保留 UI 偏好兼容 |

## 四、兼容层规则

1. **只读旧数据，写新数据**：迁移期可以读旧 key，但所有写操作只写新 store。
2. **不双写**：禁止同时写 localStorage 和 store，否则一定分叉。
3. **旧 API 兼容**：
   - `window.jco.kernel.ask` 保留但标记 deprecated；
   - `window.jco.tasks.dispatch` 改为内部创建 Task 的兼容入口，不再直接执行；
   - `tasks.sessions` / `tasks.session` 从新 TaskRepository 读。
4. **旧页面只读适配器**：未迁移页面通过只读 adapter 读 store；不得直接读旧 key。
5. **页面路由可回退**：新视图出问题时可以临时回退到旧 iframe，但必须在同一波次内修复，不能长期保留。
6. **迁移幂等**：同一旧数据重复迁移不产生重复会话/任务。
7. **迁移前备份**：`store.backup.json` + 旧 key 导出；失败不覆盖。

## 五、跨页旅程回归

这些旅程必须整条跑通，不能只测单页：

1. 首页 → 新会话 → 聊天 → 任务卡 → 任务详情 → 审批；
2. 选题 → 创作 → 做视频 → 后期 → 发布；
3. 账号中心 → 发布任务 → 审批；
4. 自动任务 → 任务台账 → 通知 → 任务详情；
5. 技能库 → 员工角色 → 任务可用工具；
6. 设置 → BrandProfile → 选题/文案/发布提示词全部生效；
7. 对话 → 分享/重命名/删除 → 侧栏同步；
8. 旧数据迁移 → 所有页面能读到同一份历史。

## 七、全站完成定义

只有同时满足以下条件，才能说“整个项目迁移完成”：

- 迁移矩阵中所有页面为 `verified`；
- 旧业务 localStorage 只读兼容，不再写入；
- 所有页面使用统一消息/任务/状态组件；
- 所有页面提示词不再写死行业；
- 所有页面派活走 TaskService；
- 所有页面自动任务/派活/通知读同一任务台账；
- 所有跨页旅程 E2E 通过；
- 16 个现有页面 + 新任务详情的视觉回归通过；
- 安装版冒烟、真实内核/浏览器/ffmpeg 冒烟通过；
- 产品负责人按普通用户视角走完全流程。

## 八、施工顺序

```text
Wave 0 契约/兼容层
  → Wave 1 壳 + 首页 + 聊天 + 任务详情
  → Wave 2 选题 + 素材 + 创作 + 做视频 + 后期
  → Wave 3 发布 + 运营 + 账号中心
  → Wave 4 设置 + 自动任务 + 技能库 + 管家团队 + 设计系统
  → 全站跨页回归 + 安装版 + 验收
```

每一波结束都必须保持整个应用可用，不允许出现“新页面能开、旧页面读不到数据”的半迁移状态。
