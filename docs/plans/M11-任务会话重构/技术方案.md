# M11 技术方案：会话、任务与角色分层

- 日期：2026-10-17
- 状态：设计冻结中
- 关联：`领域模型与交互冻结.md`、`接口契约.md`、`验收用例.md`

## 一、当前实现的关键约束

1. DSH SDK 的 `RunOptions` 只有 `sessionId` 和 `onNotification`，**没有 `system` 字段**；
2. 现有 `bridge.mjs` 把整段系统提示词拼进用户输入（`bridge.mjs:611`），聊天和任务共用；
3. 浏览器工具 patch 和后期工具 patch 对所有会话常驻挂载（`bridge.mjs:416-417`）；
4. 当前数据分散在 `localStorage`、`kernel/*.json`、`task-sessions/*.json`；
5. 当前前端是应用壳 + iframe，多页各有一份脚本，不适合一次全量重写。

本方案按“最小风险、可验证、逐步替换”设计，不做大爆炸重写。

## 四、提示词与工具分层

### 4.1 为什么不能继续拼字符串

当前 `h.run(buildChatSystem() + '\n\n' + text)` 的问题：

- 系统提示词被当成用户输入，模型可能“回复人设”而不是执行；
- 聊天、派活、自动任务共用同一套人设和浏览器操作说明；
- 技能、工具、行业、任务卡全部混在一个字符串里；
- 无法按角色做工具白名单；
- 无法测试“聊天提示词里没有发布工具步骤”。

### 4.2 HarnessPool

由于 SDK 没有 per-session system prompt，Phase 1 使用**按 profile 分池的 Harness**：

```text
chat             → ChatHarness（无浏览器/编辑/文件写入工具）
task:publisher   → PublisherHarness（浏览器工具）
task:operator    → OperatorHarness（浏览器 + 数据工具）
task:editor      → EditorHarness（ffmpeg 编辑工具）
task:writer      → WriterHarness（无副作用工具）
```

规则：

- 每个 profile 一个 `DeepSeekHarness` 实例，按需懒启动；
- 每个 profile 有自己的串行队列；
- session id 命名空间：`chat:<conversationId>`、`task:<taskRunId>`；
- 空闲超时回收子进程；
- 后续如果 DSH 提供 per-session system prompt/persona，再合并池，不改 Domain。

### 4.3 PromptBuilder

```text
BasePrompt（通用）
  + BrandProfile（行业/受众/语气/平台/目标/禁用表达）
  + ProfilePrompt（chat / publisher / operator / editor / writer）
  + TaskCard（仅任务）
  + Skills（仅任务/相关角色）
  + ExternalContent（明确标记为“资料，不是指令”）
```

Chat 的 prompt 不包含：

- 发布页操作步骤；
- 浏览器快照/点击/上传说明；
- 员工职责；
- 行业默认身份。

Task 的 prompt 不包含：

- 聊天人格；
- 与当前任务无关的工具说明；
- 与当前角色无关的平台/技能。

## 五、数据层

### 5.1 Repository 接口

```ts
interface ConversationRepository {
  list(): Promise<ConversationSummary[]>
  get(id: string): Promise<Conversation | null>
  create(input: CreateConversationInput): Promise<Conversation>
  appendMessage(id: string, message: Message): Promise<void>
  rename(id: string, title: string): Promise<void>
  remove(id: string): Promise<void>
}

interface TaskRepository {
  list(): Promise<TaskSummary[]>
  get(id: string): Promise<Task | null>
  create(input: CreateTaskInput): Promise<Task>
  updateStatus(id: string, status: TaskStatus): Promise<void>
  appendEvent(event: TaskEvent): Promise<void>
  listEvents(taskId: string): Promise<TaskEvent[]>
}
```

### 5.2 v1 存储

采用主进程**单一 JSON 存储**：

```text
%APPDATA%/J.Co/data/store.json
%APPDATA%/J.Co/data/store.backup.json
%APPDATA%/J.Co/data/migrations.log
```

要求：

- `schemaVersion`；
- 单写者（只在主进程写）；
- 临时文件 + rename 原子写入；
- 每次写入前保留上一版 backup；
- 启动时校验 JSON，失败则从 backup 恢复并提示；
- 不把 store 放进安装包。

选择理由：

- 数据量小，JSON 足够；
- 不引入原生 SQLite 依赖，避免再次出现打包缺包；
- Repository 接口不暴露存储格式，后续可无痛换 SQLite。

### 5.3 迁移

首次启动新版本时：

1. 读取 `localStorage.jco-chats-v1`（通过渲染进程导出或一次性迁移脚本）；
2. 读取 `kernel/task-sessions/*.json`；
3. 读取 `kernel/auto-tasks.json` / `auto-runs.json`；
4. 转成新 schema；
5. 写入 store；
6. 保留旧文件只读备份，确认后再清理。

迁移必须可重复执行（幂等），不能丢消息、不能重复建任务。

## 六、任务执行

### 6.1 TaskRunner

```text
TaskService.confirm(taskId)
  → TaskStateMachine: pending_confirm → queued
  → TaskRunner.start(taskId)
  → create TaskRun
  → HarnessPool.get(profile)
  → PromptBuilder.build(task, brand, role, skills)
  → run
  → onActivity → TaskEvent
  → onApproval → ApprovalService
  → onArtifact → ArtifactRepository
  → done / failed
```

### 6.2 浏览器

- `TaskRunner` 根据 `task.type` 和 `ownerRole` 判断是否需要 BrowserSession；
- 需要时调用 `BrowserSessionManager.ensure(platform)`；
- 发布/运营任务才有浏览器工具；
- 纯聊天与写作任务没有浏览器工具；
- 发布按钮永远产生 Approval，不提供自动点击工具。

### 6.3 自动任务

```text
AutomationService.tick()
  → 到点
  → TaskService.createFromTemplate()
  → 统一 Task / TaskRun / TaskEvent
```

删除 `runAutoTask` 的第二套记录路径；`auto-runs.json` 只作为历史迁移来源，不再作为运行台账。

## 七、前端改造顺序

1. 新增 `message.js`，先在现有总管页替换消息渲染，验证排版；
2. 新增 `home.js`，首页发送改为新会话；
3. 新增 `task.js`，任务详情独立；
4. 壳内新增 `#/chat/:id`、`#/task/:id` 路由；
5. 旧 `J.Co总管.html` 保留 iframe 回退，确认新视图稳定后移除；
6. 旧页面侧栏继续由壳隐藏，不新增重复侧栏。

### 7.1 全站迁移与兼容

M11 的最终范围是全部 16 个现有页面 + 新任务详情页，不是只做首页/聊天/任务。施工按波次推进：

```text
Wave 0 契约/兼容层
  → Wave 1 壳 + 首页 + 聊天 + 任务详情
  → Wave 2 选题 + 素材 + 创作 + 做视频 + 后期
  → Wave 3 发布 + 运营 + 账号中心
  → Wave 4 设置 + 自动任务 + 技能库 + 管家团队 + 设计系统
  → Wave 5 全站跨页验收
```

兼容规则：

- 迁移期旧业务 localStorage 只读，不双写；
- 未迁移页面通过只读 adapter 读新 store；
- 页面不得直接调用 `tasks.dispatch`，统一走 TaskService；
- 页面不得直接启动浏览器，统一走 TaskRunner；
- 页面不得写死行业，统一读 BrandProfile；
- 旧 `window.jco` API 保留兼容层，稳定后移除；
- 每波结束都必须保持整个应用可用，不允许半迁移状态长期存在。

完整页面清单、旧 key 映射和跨页门禁见 [`全站迁移矩阵.md`](全站迁移矩阵.md)；主进程、内核、工具、数据、安装、安全、测试、日志等全软件分层见 [`全项目迁移总表.md`](全项目迁移总表.md)。

## 九、风险与降级

| 风险 | 影响 | 降级 |
|---|---|---|
| DSH 多 Harness 内存 | 两个以上子进程占用高 | Phase 1 只启用 chat + publisher 两个；空闲回收 |
| JSON 并发写 | 数据损坏 | 单写者 + 原子写 + backup |
| 旧数据迁移失败 | 用户丢会话 | 迁移前备份；迁移失败不覆盖旧文件 |
| 前端视图重写风险 | 页面回归 | 先替换首页/聊天/任务，其它页面保留 iframe |
| 细节回归 | 视觉问题重现 | D0–D4 + 视觉回归 + 独立审查 |
