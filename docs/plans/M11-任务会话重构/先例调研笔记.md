# M11 先例调研笔记：会话、任务与细节质量

- 日期：2026-10-17
- 目的：为 M11 的领域模型、交互冻结、测试与细节门禁提供可查证的业界依据。

## 一、找什么

1. AI 辅助开发为什么“大框架可以、细节容易垮”；
2. 成熟团队如何把细节变成可验证的工程对象；
3. 会话、任务、自动化、Agent 角色如何划分边界；
4. 如何用测试、截图对比、规范和审查兜住细节；
5. 如何避免一次性大重写。

## 二、找到了什么

### 1. Addy Osmani：The 70% problem

出处：https://addyo.substack.com/p/the-70-problem-hard-truths-about

关键结论：

- AI 能快速做到 70%，最后 30% 收益递减；
- 典型问题是错误提示、边界条件、UI 状态、可访问性、性能；
- “Demo-quality trap”在真实用户面前会暴露；
- 有效模式是 AI 初稿 + 人工重构 + 错误处理 + 严格测试 + 关键决策记录。

抄什么：

- 每个功能设“细节预算”；
- 主路径之外必须验空态/错误/长文本/慢加载/边界数据；
- 人的审美和最终验收不可省。

不抄什么：

- 不把“最后 30% 只能靠人”理解成“AI 不用管细节”；
- 不让 AI 只交 demo，再由人全量补。

### 2. Anthropic：Claude Code best practices

出处：https://www.anthropic.com/engineering/claude-code-best-practices

关键结论：

- 给 AI 一个能运行、能读出通过/失败的验证回路；
- UI 改动给参考图，让 AI 截图、对比、列差异、修复；
- 要求展示证据，不接受口头“完成”；
- 先探索、再计划、再实现；
- 具体上下文和约束比模糊形容词有效。

抄什么：

- D2 自动检查 + D4 证据；
- 截图对比回路；
- 小步计划、及时纠偏；
- 每次 UI 交付附差异清单。

### 3. GitHub Spec Kit

出处：

- https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/
- https://github.com/github/spec-kit

关键结论：

- AI 像字面理解的结对程序员，需要无歧义规范；
- Specify → Plan → Tasks → Implement；
- 每个任务小到可单独实现、单独测试；
- 每阶段有检查点；
- 设计系统、安全、性能约束进入 spec/plan。

抄什么：

- M11 的四件套：立项单、领域模型/交互冻结、技术方案、接口契约、验收用例；
- 小任务 + 检查点；
- 细节任务卡。

### 4. Simon Willison：负责任地用 AI 写代码

出处：https://simonwillison.net/2025/Mar/19/vibe-coding/

关键结论：

- vibe coding = 不 review、不理解、不测试；
- 生产质量要读代码、测试、能解释；
- 不能解释的代码不提交。

抄什么：

- 关键路径必须 review；
- Domain 状态机、数据迁移、工具权限必须可解释、可测试；
- 禁止“AI 生成了就算完成”。

### 5. Playwright 视觉回归

出处：https://playwright.dev/docs/test-snapshots

关键结论：

- `toHaveScreenshot()` 生成基准截图并自动对比；
- 可设阈值、遮罩动态区域、文本快照；
- 适合排版、间距、对齐、深浅色、不同窗口宽度。

抄什么：

- 聊天消息、任务详情、任务卡、空态、错误态都建视觉基准；
- 固定窗口、字体、主题、测试数据；
- 视觉回归作为失败门禁。

### 6. NN/g 与 WCAG

出处：

- https://www.nngroup.com/articles/ten-usability-heuristics/
- https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/
- https://www.w3.org/TR/WCAG22/
- https://www.w3.org/WAI/test-evaluate/

关键结论：

- 状态可见、语言贴近用户、用户可控、一致性、防错、识别而非记忆、极简、错误恢复；
- 可访问性要测对比度、焦点、键盘、标签、减少动画。

抄什么：

- 任务状态徽标、审批提示、错误恢复；
- 聊天/任务详情的键盘与焦点测试；
- 文案表和术语表；
- axe/WCAG 检查。

### 7. 领域建模与状态机

出处：

- https://martinfowler.com/bliki/BoundedContext.html
- https://c4model.com/
- https://www.eventstorming.com/
- https://stately.ai/docs/xstate

关键结论：

- 会话、任务、员工、浏览器是不同 bounded context；
- 用 C4 表达容器/组件关系；
- 用 Event Storming 找领域事件和边界；
- 用显式状态机表达任务生命周期。

抄什么：

- Conversation / Task / TaskRun / Automation / AgentRole / BrowserSession 分层；
- Task 状态机；
- TaskEvent 只追加；
- C4 上下文图和事件清单。

### 8. 渐进式替换

出处：https://martinfowler.com/bliki/StranglerFigApplication.html

关键结论：

- 用新实现逐步包住旧实现，按路由/功能切片替换；
- 不做一次性大爆炸重写。

抄什么：

- Phase 1 只替换首页、聊天、任务详情；
- 其它页面继续 iframe；
- 旧 API 保留兼容层，稳定后移除。

## 三、对 M11 的直接结论

1. 先做领域模型和交互冻结，不直接改页面；
2. 会话和任务必须是不同对象、不同页面、不同数据；
3. 提示词和工具按 profile 分层，聊天不挂浏览器；
4. 自动任务只创建 Task，统一台账；
5. 数据先 JSON + Repository，后续可换 SQLite；
6. 细节按 D0–D4 门禁，不接受结构断言；
7. Phase 1 只做一条纵向链路，其它页面渐进替换。
