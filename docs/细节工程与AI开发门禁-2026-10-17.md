# J.Co 细节工程与 AI 开发门禁

> 结论先行：AI 擅长把大框架快速做到 70%，最后 30% 的细节不会因为“再提醒它一次”就自动稳定。成熟做法是把细节变成**可列出的清单、可运行的断言、可比较的截图、可复核的证据**，再加上人的审美和最终验收。
>
> 这不是“AI 不行”，而是 AI 需要一个**能告诉它哪里不对、并且能反复验证到通过**的闭环。

---

## 一、公开资料怎么说

### 1. Addy Osmani：AI 辅助开发的“70% 问题”

出处：[The 70% problem: Hard truths about AI-assisted coding](https://addyo.substack.com/p/the-70-problem-hard-truths-about)

核心结论：

- 非工程师用 AI 可以很快做到 70%，但最后 30% 会进入收益递减；
- 典型问题不是“功能跑不起来”，而是错误提示看不懂、边界条件崩溃、UI 状态混乱、可访问性被忽略、慢设备性能差；
- 他把这称为“Demo-quality trap”：演示很漂亮，真实用户一用就散；
- 他给出的有效模式是“AI 初稿 + 人工重构 + 补错误处理 + 严格测试 + 记录关键决策”；
- 他的判断很直接：真正打磨到消费者质量，靠的是同理心、经验和对工艺的在意，不能默认 AI 会替你完成。

对我们的意义：

- 不能把“页面能打开、按钮能点”当成完成；
- 必须专门为错误态、空态、长文本、慢加载、边界数据、可访问性和真实用户动线写验收；
- 每个功能都要有“细节预算”，不能只验收主路径。

### 2. Anthropic：给 AI 一个能验证工作的回路

出处：[Best practices for Claude Code](https://www.anthropic.com/engineering/claude-code-best-practices)

核心结论：

- 给 AI 一个它能运行、能读出通过/失败的检查：测试、构建、lint、截图对比；
- 没有检查时，“看起来完成了”就是唯一信号，人就会变成验证回路；
- UI 改动要提供参考截图，让 AI 实现后自己截图、对比、列出差异、修复；
- 要求 AI 展示证据，而不是只说“已完成”；
- 工作顺序是：先探索、再计划、再实现；复杂改动要有计划，不要直接开写；
- 代码要给足具体上下文、约束和示例，模糊提示会换来模糊结果。

对我们的意义：

- 现在很多门禁只验证“元素存在”，AI 当然会停在“结构看起来对”；
- 需要新增视觉回归、几何断言、文案快照、长文本/空态/错误态检查；
- 每次 UI 任务都要求 AI 提供截图和差异清单，不接受口头完成。

### 3. GitHub Spec Kit：把细节写进可执行规范

出处：[Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)

核心结论：

- AI 像“字面理解的结对程序员”，很擅长模式识别，但需要无歧义指令；
- 流程是 Specify → Plan → Tasks → Implement；
- 每个任务要小到可以单独实现、单独测试；
- 每个阶段都有检查点，不能没验证就进入下一阶段；
- 设计系统、安全约束、性能目标应该进入 spec/plan，而不是事后补；
- AI 负责生成产物，人负责确认这些产物是否真的对。

对我们的意义：

- “做一个聊天页”不是任务；“消息组件支持 8 种状态、3 种窗口宽度、深浅色、长文本、复制/引用/删除”才是任务；
- 细节必须写进任务卡，不能靠实现时临场发挥；
- 每做完一个组件就停下来验收，不把十个页面的细节堆到最后。

### 4. Simon Willison：负责任地用 AI 写代码

出处：[Not all AI-assisted programming is vibe coding](https://simonwillison.net/2025/Mar/19/vibe-coding/)

核心结论：

- “vibe coding”是指不 review、不理解代码、完全交给 AI；
- 生产质量的做法是：读代码、测试、能向别人解释这段代码做什么；
- 他的黄金规则是：如果不能解释清楚一段代码，就不提交它。

对我们的意义：

- 不能因为 AI 生成了就默认正确；
- 关键路径必须有代码审查和可解释性；
- 对 UI 细节，至少要能解释“为什么这个字号、间距、宽度、状态是这样”。

### 5. Playwright：视觉细节可以回归

出处：[Visual comparisons](https://playwright.dev/docs/test-snapshots)

核心结论：

- 可以用 `toHaveScreenshot()` 生成基准截图，后续运行自动对比；
- 可以设置像素差异阈值、遮罩动态区域、对文本做快照；
- 适合盯住排版、间距、对齐、深浅色、不同窗口宽度等“人眼容易漏、改一次就可能坏”的细节。

对我们的意义：

- 对话消息、任务详情、空态、错误态、侧栏展开/收起都应该有视觉基准；
- 视觉回归不是“截图存档”，而是每次改动的失败门禁；
- 截图对比要固定窗口尺寸、字体、主题和测试数据。

### 6. NN/g 与 WCAG：细节有成熟检查维度

出处：

- [10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)
- [Heuristic Evaluations: How to Conduct](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- [W3C WAI: Evaluating Web Accessibility](https://www.w3.org/WAI/test-evaluate/)

可直接用于 J.Co 的检查维度：

- 系统状态可见：AI 在干什么、到哪一步、为什么停下；
- 语言贴近用户：不把内部错误码、工具名、模型术语丢给普通用户；
- 用户可控：能取消、能返回、能撤销、能重试；
- 一致性：同一件事在全站用同一种说法、同一种按钮、同一种状态；
- 防错：危险动作二次确认，发布/删除/支付永远人工；
- 识别而非记忆：重要信息和下一步要可见，不让用户记上一页；
- 极简：不堆无关信息，优先展示当前任务最重要的内容；
- 错误恢复：错误信息要说明发生了什么、能做什么；
- 可访问性：对比度、焦点态、键盘操作、标签、减少动画。

## 二、为什么 J.Co 之前总是“框架对、细节烂”

### 2.1 门禁验证了结构，没有验证细节

现有测试大量检查：

- 元素是否存在；
- 文本是否包含某个词；
- 源码里是否有某个调用；
- 页面是否能加载。

这些检查能证明“骨架在”，但不能证明：

- 消息是否像聊天记录；
- 字号、行高、宽度是否舒服；
- 长文本是否被截断；
- 空态、错误态、加载态是否完整；
- 键盘能否操作；
- 1280 宽度下是否溢出；
- 深浅色是否一致；
- 用户能不能不看说明完成任务。

### 2.2 任务粒度太大

“把聊天页做好”是一个太大的任务。AI 会优先满足显眼的结构，细节被留到最后；而最后往往没有时间。

应该拆成：

```text
消息容器布局
用户消息样式
AI 消息排版
Markdown 渲染
长文本与代码块
复制/引用/删除操作
空态/加载态/错误态
深浅色
1280/1440 响应式
键盘与焦点
视觉回归
```

每个小任务都有自己的验收标准，才不会出现“大框架没问题，细节全靠人补”。

### 2.3 没有“细节资产”

细节不能每次靠临场感觉。需要固定资产：

- 设计 token：字号、行高、间距、圆角、颜色、阴影；
- 组件状态矩阵：default / hover / focus / active / disabled / loading / empty / error；
- 文案表：按钮、空态、错误、确认、成功提示；
- 参考截图：什么算“对”，什么算“不对”；
- 真实数据样本：长文本、空数据、超长标题、特殊字符、慢加载；
- 视觉基准截图；
- 已知取舍清单。

没有这些资产，AI 每次都会重新猜，细节就会每次重新坏。

### 2.4 AI 没有“失败信号”

Anthropic 的提醒很关键：没有可运行的检查时，“看起来完成”就是唯一信号。J.Co 之前很多 UI 任务就是这样停在了“看起来完成”。

解决办法不是让 AI “再仔细一点”，而是给它：

- 一张参考图；
- 一组必须通过的截图；
- 一组必须通过的几何/文本断言；
- 一份必须逐项填写的细节清单；
- 一个独立审查者。

## 三、J.Co 细节分类与检查矩阵

| 细节类别 | 典型问题 | 必须有的资产 | 自动检查 | 人工检查 |
|---|---|---|---|---|
| 视觉 | 字号、行高、间距、对齐、层级、圆角、阴影 | design token、组件状态图、参考截图 | 视觉回归、几何断言 | 设计走查 |
| 交互 | hover/focus/disabled、键盘、滚动、取消、重试 | 交互状态矩阵 | Playwright 操作、焦点断言 | 键盘走一遍 |
| 文案 | 术语不统一、错误看不懂、空态没话说 | 文案表、术语表 | 文本快照 | 普通用户阅读 |
| 数据 | 长文本截断、空数据、特殊字符、分页、排序 | 真实数据样本 | 数据驱动测试、快照 | 边界数据手测 |
| 行为 | 超时、并发、重复点击、失败恢复、幂等 | 状态机、错误码表 | 单元/集成测试 | 故障演练 |
| 可访问性 | 对比度、标签、焦点顺序、减少动画 | 无障碍规范 | axe、键盘测试 | 读屏/键盘走查 |
| 性能 | 长会话卡顿、大图、慢加载 | 性能预算 | 长列表/大文件测试 | 真机体感 |
| 安全 | 工具越权、数据泄露、危险点击 | 权限矩阵、审批点 | 契约测试、静态检查 | 对抗审查 |

## 四、细节门禁 D0–D4

每个具体任务直接复制 [`细节任务卡模板.md`](细节任务卡模板.md) 使用。

### D0：设计契约

在写代码前必须有的内容：

- 参考截图或线框；
- 设计 token（字号、行高、间距、颜色、圆角、阴影）；
- 组件状态矩阵；
- 文案表；
- 响应式规则（至少 1280×800、1440×900）；
- 深浅色规则；
- 明确的非目标。

没有 D0，不允许开始 UI 实现。

### D1：实现契约

每个组件/页面的任务卡必须写清：

- 输入和输出；
- 所有状态：default / hover / focus / active / disabled / loading / empty / error；
- 长文本、空数据、特殊字符、网络失败；
- 键盘操作和焦点顺序；
- 与现有组件的关系；
- 验收证据。

### D2：自动检查

最低要求：

- `typecheck`；
- `lint`；
- 单元测试；
- 关键组件视觉回归；
- 关键布局几何断言；
- 文案/数据快照；
- 可访问性扫描；
- 长文本、空态、错误态、深浅色、窄窗口；
- 安装版冒烟。

### D3：独立审查

三层审查，不能省：

1. **AI 自审**：对照 D0/D1 清单逐项打勾，列出未完成项；
2. **对抗审查**：另一个 AI 会话专门找“哪里不像真实产品、哪里会坏、哪里文案不对”；
3. **人的设计 QA**：产品负责人只用页面可见信息走一遍，不看源码、不看测试 ID。

### D4：交付证据

每次 UI 交付必须附：

- 改动前后的截图/录屏；
- 视觉回归结果；
- 关键状态截图（空/加载/错误/长文本/深浅色/窄窗口）；
- 已知差异和取舍；
- 未解决项清单。

没有证据，不叫完成。

## 五、怎么让 AI 在开发时主动处理细节

### 5.1 提示词要给“验收信号”，不要给形容词

不要写：

```text
把聊天页做得好看一点、精致一点。
```

要写：

```text
参考这张截图实现消息列表。

要求：
1. AI 消息左对齐，头像 32px，正文最大宽度 720px，字号 14.5px，行高 1.7；
2. 用户消息右对齐，气泡最大宽度 70%；
3. 段落间距 10px，列表有 16px 左缩进，代码块有背景和横向滚动；
4. 支持空态、加载态、错误态、长文本、深浅色；
5. 1280×800 和 1440×900 不溢出；
6. 实现后自己截图，和参考图逐项对比，列出差异并修复；
7. 交付时附截图、差异清单和未完成项。
```

### 5.2 先让 AI 产出“细节清单”，再让它写代码

在 Plan 阶段要求：

```text
先不要写代码。列出这个组件的：
- 所有状态
- 所有边界数据
- 所有文案
- 所有尺寸/间距/字号
- 所有键盘操作
- 所有错误和空态
- 所有验收证据
我确认清单后再实现。
```

这一步能把“细节”从隐性变成显性。

### 5.3 要求 AI 截图对比，而不是口头汇报

每轮 UI 实现后：

```text
截图当前结果，和参考图逐项比较：
字号、行高、间距、宽度、对齐、颜色、圆角、阴影、溢出、空态、错误态。
列出差异，修复，再截图，直到没有差异或差异有明确理由。
```

### 5.4 要求 AI 展示证据

完成时要求：

```text
不要只说完成。给我：
1. 运行了哪些检查；
2. 每条检查的结果；
3. 关键截图；
4. 还没解决的问题；
5. 你认为需要我拍板的取舍。
```

### 5.5 小步提交，不要攒大改

- 一次只做一个组件/一条动线；
- 每个小步都有截图和检查；
- 不用“最后统一调样式”；
- 不用“等所有页面做完再验收”。

## 六、J.Co 聊天消息组件的细节样例

这是当前截图问题的具体落地标准，可以作为第一个细节样板。

```text
布局：
- 会话内容从上往下排列，第一条消息从顶部开始；
- 输入框固定在底部，不随消息数量漂移；
- 消息区域最大阅读宽度 720–760px，居中；

AI 消息：
- 左侧头像 32px，名字 12–13px；
- 正文 14.5px，行高 1.7；
- 不使用 84% 宽的大圆角卡片；
- 平坦正文，背景与页面一致或极浅；
- 段落间距 10px，列表左缩进 16px，代码块横向滚动；
- 链接、加粗、引用有明确但克制的样式；

用户消息：
- 右对齐气泡，最大宽度 70%；
- 背景使用 accent 或浅色 tint；
- 字号 14.5px，行高 1.7；
- 长文本可换行，不溢出；

消息操作：
- 复制、引用、创建任务、删除；
- hover 显示，focus 可见，键盘可操作；

状态：
- 空会话、加载中、流式输出、失败、重试、长文本、代码块；
- 深浅色；
- 1280×800 / 1440×900。

验收：
- Playwright 视觉回归；
- 消息宽度/间距/输入框位置的几何断言；
- 长文本不截断；
- 键盘 focus 可见；
- 截图对比无未解释差异。
```

## 七、J.Co 的细节 Definition of Done

一个 UI 改动只有满足以下条件才算完成：

- [ ] 有 D0 设计契约（参考图、token、状态、文案、响应式）；
- [ ] 有 D1 实现契约（状态矩阵、边界数据、键盘、错误）；
- [ ] 所有状态都有截图或测试；
- [ ] 长文本、空数据、错误、加载、深浅色、窄窗口都验过；
- [ ] 视觉回归通过；
- [ ] 键盘/焦点/可访问性检查通过；
- [ ] 安装版冒烟通过；
- [ ] 有改动前后对比和已知差异；
- [ ] 产品负责人按普通用户视角验收通过；
- [ ] 文档和任务卡同步更新。

缺少任何一项，都只能叫“实现了一部分”，不能叫“完成”。

## 九、结论

细节不是“AI 做不到”，而是“没有被做成可验证的东西”。

J.Co 以后每个功能都按这个顺序走：

```text
设计契约 → 细节清单 → 小步实现 → 截图对比
→ 自动断言 → 独立审查 → 人的最终验收
```

人的作用不是替 AI 擦屁股，而是定义什么算“好”、什么算“不能接受”、最终拍板。AI 的作用是把清单执行、把差异找出来、把回归跑起来。
