# J.Co 专业质量保障体系与大厂测试调研

> 日期：2026-10-20
> 适用版本：从 `0.6.0-beta.27` 起
> 目标：把“能跑门禁”升级成“能发现真实用户问题、能阻止发布、能追溯证据、能快速回退”的质量体系。

## 一、先说结论

软件工程不存在“测试后保证零 BUG”的数学证明。大厂也不会只依赖一套全绿门禁，而是同时建设：

1. 快速反馈的 PR 检查；
2. 全量、跨平台、分片执行的主干验证；
3. 真实用户路径的 E2E；
4. 可重复的视觉、快照和安装包验证；
5. 真外部服务的独立测试通道；
6. 自动化探索与故障注入；
7. 发布候选逐字节认证、签名、灰度和回滚。

本轮把 J.Co 原有的“门禁”升级为上述体系的第一版可执行实现。目标不是宣称永不出错，而是让**已知高风险功能必须有人机可读的证据、未知问题能被自动探索更快暴露、坏包无法被误当正式包交付**。

## 二、大厂公开实践

### 2.1 OpenAI Codex

参考仓库：[openai/codex](https://github.com/openai/codex)

公开仓库可确认的做法：

- `.github/workflows/blocking-ci.yml` 是唯一阻断合并入口，最后用 `always()` 汇总所有必需任务，避免上游失败后被误报为成功。
- PR 路径以 Bazel `test` + `clippy` 为主，追求快速反馈；主干再跑完整 Cargo `nextest` 矩阵、跨平台构建、release profile 构建和 remote-env 测试。
- Windows、macOS、Linux 分开执行；Windows 测试按 4 个分片运行，并上传 JUnit 报告。
- release workflow 不只编译，还对准备发布的精确产物执行包测试、符号检查、签名和校验。
- Rust 之外还有 Python SDK、并发兼容性、文档检查、拼写检查、依赖策略和 blob 大小策略。

可借鉴的核心：

- **快速 PR 门与全量主关门分层**；
- **同一候选版本跨平台、分片执行**；
- **验证准备发布的同一份字节，而不是另编一份**；
- **单一聚合状态，防止假绿**。

### 2.2 Anthropic Claude Code

参考：

- [Claude Code 最佳实践](https://www.anthropic.com/engineering/claude-code-best-practices)
- [长运行 Agent 的有效 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [anthropics/claude-code](https://github.com/anthropics/claude-code)

公开资料可确认的做法：

- 官方最佳实践把“给 Claude 一个可运行的验证闭环”列为核心：测试、构建退出码、Lint、fixture diff、浏览器截图。没有验证闭环时，模型只能以“看起来完成”为完成标准。
- 强调每一步展示证据，而不是只说成功：测试输出、执行命令、截图结果。
- UI 改动要求让 Agent 截图并与目标对比，列出差异后继续修。
- 长任务 Harness 使用结构化 feature list，初始状态全部标记为未通过；每个会话只推进一个功能；用进度文件、git 提交和端到端浏览器操作维持跨上下文状态。
- 公开仓库的 mods 测试会先 TypeScript typecheck，再逐个包运行插件测试；基础设施变更也有独立的 workflow hardening 检查。
- 公开仓库的 Agent 工作流配置了 egress firewall、网络 allow list、最小权限和 `--permission-mode auto`，说明“让 AI 自动跑测试”本身也必须受权限和网络边界约束。

可借鉴的核心：

- **验证闭环是产品能力，不是测试同学的附加步骤**；
- **功能账本 + 每项证据 + 一次只推进一项**；
- **浏览器按真实用户方式操作，并保存截图/报告**；
- **自动化 Agent 使用最小权限、网络白名单和可审计动作**。

### 2.3 DeepSeek Harness（DSH）

参考仓库：[deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)

公开仓库可确认的做法：

- 将静态检查、覆盖率、benchmark、snapshot/artifact、consumer 兼容测试、Node 多版本兼容、Python SDK、Windows build/coverage/native tests 分成独立 job，再统一聚合。
- 覆盖率按分区执行；保存覆盖耗时历史用于治理慢测试。
- 有 Web/UI snapshot、性能、压力测试脚本，以及大量文档、包元数据、包依赖、安装布局和运行闭包检查。
- 真实 DeepSeek API E2E 独立于无密钥门禁：只在可信事件运行，明确固定 base URL，且先做密钥 preflight；密钥缺失直接失败，防止测试自跳过被当成全绿。
- Windows 打包 workflow 会校验源码 ref 必须是允许的分支或 tag、tag 与 package 版本一致、checkout 与 tag 一致；打包后验证真实 packaged runtime，再保留安装包和完整诊断。

可借鉴的核心：

- **无密钥确定性测试和真实 API 测试必须分开**；
- **测试自跳过必须有 preflight，防止假绿**；
- **包版本、源码 ref、tag 和候选产物必须四方一致**；
- **性能、快照、安装布局和运行闭包都属于质量门**。

### 2.4 腾讯 Marvis

参考：

- [Marvis 官网](https://marvis.qq.com/)
- [Marvis 产品认知与定位](https://marvis.qq.com/docs/product-description)

公开资料可确认的产品特征：

- 能读取本地文件、调用系统能力、进入网页、调用应用，并支持跨设备任务接续。
- 明确区分本地隐私模式和端云协同模式。
- 涉及隐私、安全、支付和高风险电脑操作时，交还用户确认。

公开渠道没有找到 Marvis 的工程测试流水线白皮书。因此本轮只把它用于**风险建模**，不虚构其内部测试细节：

- 高风险工具必须有权限边界和确认点；
- 本地数据与云端数据要有不同测试路径；
- 长任务必须能暂停、恢复、取消和查询；
- 任务执行过程必须可观察，失败要保留结果和原因。

## 三、J.Co 质量体系

### 3.1 分层模型

| 层级 | 要回答的问题 | J.Co 当前实现 |
|---|---|---|
| L0 源码契约 | 样式、页面和依赖是否违反同一来源 | `check-ui-source.mjs`、`audit-frontend.mjs`、Biome、TypeScript、项目扫描 |
| L1 单元 | 纯逻辑、状态机、解析器、路径守卫是否正确 | Vitest，当前 194 passed / 1 skipped |
| L2 UI 契约 | 同类按钮、开关、输入、卡片是否真的同一尺寸和实际轮廓 | `ui-inventory.mjs`（382 个圆角元素）、`m16-ui-contract` |
| L3 集成 | IPC、任务台账、数据迁移、媒体任务是否正确 | 单元测试 + E2E 中的 Task/Store/Kernel 链路 |
| L4 用户旅程 | 真实用户从页面 A 到结果是否完整可用 | 65 条 Playwright Electron E2E |
| L5 自主探索 | 没人手点每个 tab 时，异常状态能否被自动发现 | `m17-autonomous-ui`：安全控件探索、随机导航、故障数据注入 |
| L6 视觉 | 布局、间距、状态外观是否回退 | 17 张 1440×900 关键状态基准 |
| L7 安装包 | 打包后的真实产物能否启动、用 UI、连内核 | `qa-packaged`、`qa-installed-ui`、`verify-packaged-kernel` |
| L8 真外部 | 模型、浏览器、平台页面是否仍可用 | `test:live-media`、真实浏览器/ffmpeg 专项，归入发布前认证 |

### 3.2 功能质量矩阵

新增 [`app/quality/feature-matrix.json`](../app/quality/feature-matrix.json)，每项功能记录：

- 所属页面；
- P0/P1/P2 优先级；
- 风险描述；
- 自动化证据文件；
- `covered` / `partial` 状态；
- `partial` 必须写清楚人工边界。

`quality-report.mjs --check` 会阻止以下情况：

- 某页面没有进入矩阵；
- P0/P1 功能没有任何自动化证据；
- 证据文件不存在；
- P0 的 E2E 全部只做源码字符串检查，没有任何真实交互或视觉断言；
- `partial` 不写人工边界；
- 功能 ID 重复。

### 3.3 全站操作控件契约

本轮统一定义 4 类操作控件：

| 类型 | 规格 | 使用场景 |
|---|---|---|
| 标准文本操作 | 36px 高、10px 圆角、左右 14px、13px 字 | 主要/次要文本按钮 |
| 紧凑操作 | 30px 高、8px 圆角、左右 10px、12px 字 | 参数、筛选、分段选择 |
| 圆形图标 | 40px 直径 | 发送、播放、悬浮总管 |
| 方形图标 | 32px、8px 圆角 | 关闭、更多、通知、消息操作 |

开关统一 44×26，圆钮 22px，无页面级阴影。实际几何轮廓统一由共享层定义：正圆和胶囊使用 `corner-shape: round`，矩形控件使用 `superellipse(1.5)`。页面内联样式禁止覆盖 `corner-shape`，避免出现“尺寸一样但一个是椭圆、一个是圆角矩形”。

`ui-inventory.mjs` 实际启动应用、遍历 15 页、读取浏览器计算样式，而不是 grep CSS。当前覆盖 188 个操作控件和 382 个圆角元素，检查同名组件跨页面实际轮廓一致；`m16` 把它放进 E2E；`check-ui-source.mjs` 禁止页面内联样式再次写死同类控件的尺寸、圆角、内边距或 `corner-shape`。

### 3.4 自主探索测试

`m17-autonomous-ui.spec.mjs` 不依赖人工输入，自动完成：

1. 遍历 15 页；
2. 点击每页可见的 tab 与分段选择器；
3. 检查按钮可访问名称；
4. 检查重复 DOM ID；
5. 检查过小操作控件；
6. 检查横向溢出；
7. 检查页面 JS 错误；
8. 用固定随机种子执行 48 次跨页导航；
9. 检查 iframe 缓存上限和页面正文；
10. 注入损坏的页面草稿 JSON，验证启动不崩。

本轮第一次运行就发现了后期页残留的第二个 `id="panel"`，这是原有 58 条 E2E 和视觉基准都没有发现的真实结构缺陷。该重复 ID 与旧编辑器残片已删除。

`m18-create-picker-shell.spec.mjs` 进一步规定：跨页交接必须走真实应用壳，不能直接对顶层窗口 `location.href` 绕过 iframe 缓存。它复现并关闭了“素材选择页被当成创作页复用”和“缓存创作页收不到已选素材”两个真实缺陷。

`m19-cross-page-handoff.spec.mjs` 把同一原则扩展到状态交接：选题→文案/创作、创作→发布都必须通过 `jcoGo()` 和 `__jcoHandoff` 送到缓存页；切走再回来，交接主题和标题不能丢。

### 3.5 安全动作策略

自主探索只点本地、可逆、无外部副作用的 tab 和 segment。以下动作永不自动执行：

- 发布、删除、支付；
- 平台登录、扫码、账号授权；
- 外部发送、评论提交；
- 真实模型生成与消耗额度；
- 文件导入/导出和系统设置写入。

需要覆盖这些路径时，使用：

- 假内核、假媒体桥和隔离用户目录；
- Task + Approval 结构测试；
- 真实外部动作的人工冒烟。

### 3.6 发布候选认证

新增 `release-certify.mjs`，对同一安装包执行：

1. 包存在性、SHA-256；
2. 打包版启动冒烟；
3. 安装版 15 页 UI 契约；
4. 安装版页面缓存与工作态；
5. 安装版真实内核 `ready:true` 和模型回复；
6. 输出机器可读认证报告。

发布门规则：

- `npm run gate` 未全绿，不进入打包；
- 安装包未跑 `qa:release`，不进入交付；
- 发布前必须备份用户数据并核对核心数据哈希；
- 每个版本保留源码存档、回滚说明、安装包 SHA-256；
- 包版本、源码提交、源码存档和回滚说明必须指向同一候选。

## 四、无人干预 AI 测试怎么保证不“假绿”

### 4.1 功能账本

AI 不看“还有多少时间”，只看功能账本里仍未 covered 的 P0/P1 项。每完成一项，只能更新证据字段，不能删除测试来换取通过。

### 4.2 可执行 Oracle

AI 可以生成操作，但必须由确定性 Oracle 判断：

- 页面 ready；
- 正文非空；
- 无 JS 错误；
- 无重复 ID；
- 控件尺寸符合契约；
- 输入/滚动状态保留；
- 任务状态机不越级；
- 产物真实存在；
- 安装包哈希与版本一致。

不把“AI 觉得没问题”当通过标准。

### 4.3 固定种子与可复现

自主导航使用固定种子；失败时记录第几次导航、页面、错误、缓存状态。复跑能重现同一个序列。

### 4.4 假绿防线

- 测试自跳过不等于通过；
- P0 证据不能只有源码字符串检查；
- 功能矩阵缺页直接失败；
- `partial` 必须写人工边界；
- 打包认证必须使用安装后的真实 exe；
- 视觉基准更新后必须再跑一次非更新模式。

### 4.5 证据产物

- `quality/generated/ui-inventory.json`：实际控件清单；
- `quality/generated/quality-report.json`：功能覆盖矩阵；
- Playwright HTML、截图和 trace；
- 视觉基准图；
- `quality/generated/release-certification.json`：安装包认证。

## 五、不能承诺什么

以下问题无法靠一次自动化测试证明永远不存在：

- 外部平台 DOM 随时改版；
- 模型输出天然非确定；
- 原生文件选择器、系统通知、托盘、扫码登录；
- GPU、字体、缩放和不同 Windows 版本造成的视觉差异；
- 新需求本身引入的新行为。

因此发布后仍需要：

- 每次发版跑真实内核/媒体/浏览器专项；
- 外部平台发布前人工确认；
- 线上问题按 P0/P1 回灌功能矩阵，先补失败测试再修；
- 安装包保留可回滚版本。

## 六、没有照搬的做法

- 不把 Codex 的 Bazel/Cargo 全矩阵照搬到 Electron 项目：J.Co 的核心风险在 UI 状态、IPC、后台任务和安装包，直接增加一套 Bazel 只会增加维护成本。
- 不把 DSH 的真实 API E2E 放进每次普通 PR：真实模型有费用、限流和非确定性，必须独立为受控 nightly/release 通道。
- 不采用“测试命令不存在就跳过并返回成功”的做法：J.Co 的质量矩阵要求 P0/P1 有真实证据，跳过不能算通过。
- 不把 Claude Code 的插件结构照搬到当前无框架页面：先保留现有单壳架构，用共享 CSS、共享脚本和 E2E 契约实现同等约束。
- 不照搬 Marvis 的跨设备能力：J.Co 当前是本地桌面工具，跨端不是现有产品范围；只借鉴其高风险确认、任务可恢复和本地隐私边界。
